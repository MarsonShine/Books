# 读懂 .NET 11 性能改进：从 JIT 到异步、集合与网络

一个接口请求要读取数据、解析 JSON、执行查询，再把结果写回网络。业务逻辑可能只有几十行，运行时却要为它处理类型分派、异步挂起、内存分配、线程调度和编码转换。优化这些环节，即使业务代码没有变，请求消耗的 CPU 和内存也可能下降。

Stephen Toub 于 2026-09-15 发布的 [Performance Improvements in .NET 11](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-11/) 汇集了这一版本的性能工作。本文以其目录为阅读线索，结合 .NET runtime 的设计文档和实现 PR，解释其中值得理解的机制。本文是原创中文解读，不是逐节译文；代码中的教学示例也不等同于原文基准。

资料核对日期：2026-09-22。版本相关描述以文章发布时的 .NET 11 预发布阶段为背景。涉及新 API、编译开关或平台专属实现时，应以实际使用的 SDK 和运行时为准。本文没有在本地复跑性能基准，不把上游某个微基准的倍数当作应用整体收益。

## 1. JIT：把抽象还原成真正需要执行的操作

### 接口调用的成本，还包括它挡住了哪些优化

先看一个教学例子：

```csharp
interface IPriceRule
{
    int Adjust(int price);
}

sealed class DiscountRule : IPriceRule
{
    public int Adjust(int price) => price - 5;
}

static int Quote(IPriceRule rule, int price) => rule.Adjust(price);
```

从 C# 看，`Quote` 必须接受所有合法的 `IPriceRule` 实现。生成机器代码时，如果仍不知道 `rule` 的具体类型，就需要在运行时找到实际方法。

但假如编译器能确认这里传入的一定是 `DiscountRule`，调用目标就确定了。进一步把 `Adjust` 内联进去，整个计算便可能缩成一次减法。如果 `price` 也是常量，连减法都可能提前算好。

因此，去虚拟化的价值不只是减少一次间接调用。它让后面的优化看见原先藏在方法里的操作，随后才能继续传播常量、删除无用分支，甚至消除整个临时对象。

PGO（基于运行情况的优化）提供的是另一类信息：过去经过这个调用点的对象，绝大多数属于某种类型。这属于统计结果，不能直接当成永久成立的类型保证。利用它生成快速路径时，仍然需要类型检查和处理其他类型的退路。

可以把优化后的决策理解为下面的伪代码。这里描述机器代码的选择，不是建议在业务里手写类型分支：

```text
如果 rule 的实际类型恰好是 DiscountRule：
    执行内联后的 price - 5
否则：
    按 IPriceRule 的一般规则查找并调用 Adjust
```

假如前一万次都是折扣规则、下一次换成加价规则，类型检查会把那一次送入一般路径，仍然得到正确结果。这就是带保护条件的去虚拟化（GDV）：数据决定优先优化谁，保护条件负责维持正确性。

这种变换有成本。原先只有一处调用，现在可能有类型判断、内联代码和备用调用，机器代码会变大。只有快速路径足够常见、内联后能省掉足够多的工作，这个交换才值得。运行时不会因为某个类出现过，就无条件为它复制整段方法。

这也解释了为什么刚启动时和预热后的性能可能不同。JIT 可以先较快地生成代码，再为热点方法投入更多优化成本；测冷启动与测稳定吞吐量，观察的是不同阶段。

### .NET 11 扩大了哪些机会

泛型虚方法比普通虚方法多一层问题：确定实现方法以后，还需要正确传递泛型上下文。.NET 11 的相关工作分步处理了非共享泛型虚方法，以及部分需要实例化适配入口的调用。它们让更多原本间接的调用变成可继续内联的直接调用，但不能据此推断所有泛型虚调用、所有 AOT 场景都已经采用相同优化。参见 [非共享泛型虚方法去虚拟化](https://github.com/dotnet/runtime/pull/122023)与[实例化入口支持](https://github.com/dotnet/runtime/pull/128702)。

另一个障碍是临时对象的逃逸判断。所谓“逃逸”，可以理解为：这个方法返回后，或者进入编译器无法继续分析的调用后，是否还有地方可能使用该对象？

如果对象被放进全局缓存，当然不能随当前栈帧一起消失。如果只是短暂用来完成一次计算，JIT 则可能把它放到栈上，进一步把字段拆成局部值。**写了 `new` 与最终发生堆分配，并不总是一一对应。**不过，能否这样优化取决于编译器是否完成了证明，不能当作 C# 的分配承诺。

.NET 11 有几个具体突破：

- **可空值装箱更容易被分析。**把装箱操作从不透明的运行时辅助调用中展开后，JIT 才能看到临时对象的用途。若对象最终仍要返回给调用方，分配依然有必要。[实现 PR](https://github.com/dotnet/runtime/pull/122167)
- **枚举器的转交不再轻易打断分析。**一个包装集合的 `GetEnumerator()` 返回另一个集合的枚举器，这种多绕一层的情况，现在能被条件逃逸分析识别得更好。[实现 PR](https://github.com/dotnet/runtime/pull/122946)
- **启动阶段也能避免部分无效装箱。**对非可空结构体调用 `ThrowIfNull`，值本来不可能为空。相关改进使 Tier 0 也能识别这种情况。[实现 PR](https://github.com/dotnet/runtime/pull/129392)

条件逃逸分析尤其值得理解。某个临时对象看起来可能被传给未知接口方法，但那条调用只存在于另一种类型的备用路径上。若编译器能把两条路径分清，就不必为了备用路径而让快速路径的对象也留在堆上。

### 以 foreach 为例，串起去虚拟化、内联和逃逸分析

```csharp
static int Total(IEnumerable<int> source)
{
    int total = 0;
    foreach (int item in source)
        total += item;
    return total;
}
```

这里的 `foreach` 隐藏了 `GetEnumerator`、`MoveNext`、`Current` 和清理枚举器的过程。若只能按接口理解它，每一步都要尊重任意实现。实际输入可能是列表，也可能是包装后的数组；列表的值类型枚举器经接口返回时还可能被装箱。

现在假设某条快速路径已经确定源是某种具体集合。优化会沿着下面的依赖关系展开：

```text
确定集合类型
  → 确定 GetEnumerator 的实现
  → 内联后看见枚举器的创建
  → 确定 MoveNext / Current 的实现
  → 判断枚举器是否会逃出当前计算
  → 可以时去掉堆分配，再把枚举器字段拆成局部值
```

最棘手的是备用路径。JIT 仍要保留接口调用，普通的保守分析可能因此认为“这个枚举器也许会被未知方法保存”。条件逃逸分析需要证明：快速路径创建的那个具体枚举器，不会走到不兼容类型的备用调用。证明成立后，才能针对快速路径消除分配。

这解释了为什么“包装集合只是转交了一次 `GetEnumerator`”也值得单独修复：若那一层转交打断对象来源的追踪，整条优化链都会停在它那里。上面的代码只是用来理解机制，并不承诺任意 `IEnumerable<int>` 输入都不分配。

### 装箱没有逃逸，不等于方法完全不分配

考虑 `int?` 经由 `IFormattable` 进行格式化。可空值为空时，装箱得到的是 `null`；有值时，可能需要把底层整数包装成对象。旧的辅助调用把这个过程包住，JIT 很难继续追踪；展开以后，短暂用于接口调用的包装才可能被消除。

但是格式化返回的字符串仍然是需要产生的结果。性能表中“减少了一个装箱对象”与“整次调用分配为零”不是一回事。与之相对，如果方法直接返回那个装箱对象，它就成为调用方可观察的结果，不能随当前栈帧消失。

逃逸分析还可能使对象连栈上的完整形态都不需要保留。若对象只有两个字段，所有使用又已内联，编译器可以直接保留两个值。这比“从堆搬到栈”又多走了一步：对象只是源码里的组织方式，最终执行只留下实际需要的数据。

### 无法消掉的委托，也能变得更小

并非每个委托都能局部消除。注册到事件、保存到字段或交给后续任务执行的委托，需要继续存在。[PR #99200](https://github.com/dotnet/runtime/pull/99200) 缩减了 CoreCLR 委托的布局，少用一个指针字段；在 64 位进程中相当于每个委托少占八字节。

这与逃逸分析解决的是两个问题：一个尽量避免创建对象，另一个降低必须创建的对象的成本。对大量注册回调、建立委托数组的负载，后者不会让对象数量下降，却能降低总分配量和长期占用。

实际编码时，可以继续使用接口、泛型和小方法。需要关注的是热点调用是否阻止了内联、临时对象是否真的逃逸。仅仅看到源码有接口，就提前把设计摊平成一大段代码，往往没有足够依据。

## 2. Runtime Async：运行时怎样执行异步方法

### 旧实现为什么需要状态机

```csharp
static async Task<int> ReadLengthAsync(Stream stream)
{
    byte[] buffer = new byte[128];
    int count = await stream.ReadAsync(buffer);
    return count;
}
```

假如读取尚未完成，方法需要先返回，把线程让出来。正在进行的读取仍然需要那块缓冲区，而读取完成以后，程序还得知道从哪里接着执行。

传统 C# 编译器会为异步方法生成状态机。可以把它理解为一份“执行进度和现场记录”：状态字段记住停在哪里，其他字段保存恢复后还要用的数据。状态机的 `MoveNext` 方法负责执行下一段代码，builder 则负责把成功结果或异常记入返回的任务。

下面省略了异常和上下文处理，只展示等待与恢复的主要过程：

```text
MoveNext：
    如果是第一次进入：
        发起读取，取得 awaiter
        如果读取尚未完成：
            保存 awaiter 和恢复所需的数据
            记下“下一次从读取完成后继续”
            注册读取完成后再次调用 MoveNext
            返回
    否则：
        取回之前保存的 awaiter

    从 awaiter 取得读取结果
    把结果记入这个方法返回的 Task<int>
```

`awaiter` 提供判断操作是否完成、取得结果以及安排后续执行的能力。先把这个名字理解到这里即可。

如果读取一开始就已完成，`MoveNext` 可以直接取得结果，不必暂停，也不必等别人再次调用它。**源码里有 `await`，不代表执行到这里就一定会停下来。**同样，编译器生成了状态机，也不代表每次调用都立即在堆上创建一个状态机对象；传统实现已经对同步完成等情况做了很多优化。

Runtime Async 要接手的，就是编译器过去预先安排好的这套等待、保存现场和恢复执行的工作。先看方法之间的调用，才能看出这样做有什么用。

### 把例子加上两层调用

下面用一个简化的价格计算贯穿后续讲解：先取得商品价格，加上运费，最后减去 20 元优惠。`cacheHit` 用来模拟是否命中缓存；未命中时，从文件读取价格。

```csharp
static async Task<int> LoadPriceAsync(bool cacheHit)
{
    if (cacheHit)
        return 120;

    string text = await File.ReadAllTextAsync("price.txt");
    return int.Parse(text);
}

static async Task<int> AddDeliveryFeeAsync(bool cacheHit, int deliveryFee)
{
    int price = await LoadPriceAsync(cacheHit);
    return price + deliveryFee;
}

static async Task<int> GetTotalAsync(bool cacheHit, int deliveryFee)
{
    int amount = await AddDeliveryFeeAsync(cacheHit, deliveryFee);
    return amount - 20;
}
```

假设商品价格为 120，运费传入 10，最终结果就是 110。方法之间的关系是：

```text
GetTotalAsync
    等 AddDeliveryFeeAsync 算出含运费的金额，再减 20
        等 LoadPriceAsync 取得价格，再加运费
            命中缓存就立即得到 120，否则读取文件
```

调用方可以这样取得最终任务，查询它的状态，再等待结果：

```csharp
Task<int> totalTask = GetTotalAsync(cacheHit: true, deliveryFee: 10);
Console.WriteLine(totalTask.IsCompleted);
int total = await totalTask;
```

下文说的“外部调用方”，就是这里拿着 `totalTask` 的代码。我们要比较的是它调用的三个方法内部怎样执行。

这里有一个需要先分清的区别：**整数 `120` 是计算结果，`Task<int>` 是可以查询是否完成、等待完成并取得结果的对象。**还没拿到价格时，可以先把一个未完成的任务交给调用方；价格拿到以后，再让任务变为完成状态。

后面的新旧对比只关注这三个方法。为了看清 Runtime Async 的作用，假设新版本中三个方法都已启用该特性，而且两处直接 `await` 都被 JIT 识别为可优化的调用。

### 旧实现：每层先返回 Task，上一层再从中取得结果

先走缓存命中的情况。`LoadPriceAsync` 立即得到 120，但返回给上一层的是 `Task<int>`。`AddDeliveryFeeAsync` 从这个已完成的任务里取得 120，加上运费，再返回一个结果为 130 的任务。最外层同样取得 130，减去优惠，返回结果为 110 的任务。

```text
LoadPriceAsync：      得到 120 → 返回结果为 120 的 Task<int>
                                      ↓ await 取得 120
AddDeliveryFeeAsync： 加上 10 → 返回结果为 130 的 Task<int>
                                      ↓ await 取得 130
GetTotalAsync：       减去 20 → 返回结果为 110 的 Task<int>
```

这一次谁都没有真的等文件，三个方法都可以在当前线程上接着执行。但是方法之间仍然按任务来传递结果。具体新建多少对象，还受任务缓存和其他优化影响；图里描述的是传递过程，不能直接当作分配计数。

再看中间两处 `await`：加运费的方法只是想拿到一个价格，减优惠的方法只是想拿到含运费的金额。它们没有把中间任务交给其他人，也没有在别处查询任务状态。对于这两次调用，最终需要使用的都是整数。

这就是 Runtime Async 可以减少工作的位置。

### 新实现：JIT 可以让这两层直接传递整数

传统方式下，C# 编译器在生成程序集时就把三个方法分别展开成了状态机。等 JIT 生成机器代码时，看到的已经是状态字段、`MoveNext` 和任务相关调用，需要再从这套代码里找优化机会。

启用 Runtime Async 后，C# 编译器会在编译结果中标明异步方法和等待操作，**把如何暂停、如何恢复的具体安排留给运行时和 JIT。**因此，JIT 生成 `AddDeliveryFeeAsync` 的机器代码时，能直接看出：它调用 `LoadPriceAsync`，紧接着就等待这个调用的结果。

运行时为此准备了两种调用方式，可以先理解为同一个方法有两个入口：

| 谁来调用 | 通过这个入口得到什么 |
| --- | --- |
| 按通常方式调用，要求取得一个 `Task<int>` 的代码 | 仍然得到 `Task<int>` |
| 能使用 Runtime Async 优化、并直接等待结果的异步方法 | 立即完成就直接得到整数；需要等待就得到用于安排恢复的信息 |

这两个入口由运行时提供，不需要开发者写两份方法。C# 中的返回类型也仍然是 `Task<int>`。改变发生在 JIT 生成的机器代码里：它能为符合条件的调用选择第二种入口。

用回刚才的价格计算，缓存命中时就可以这样执行：

1. `LoadPriceAsync` 得到 120，通过内部入口直接交给 `AddDeliveryFeeAsync`。
2. `AddDeliveryFeeAsync` 加上 10，把 130 直接交给 `GetTotalAsync`。
3. `GetTotalAsync` 减去 20，得到 110。假设外部调用方要拿到一个任务，就由通常入口提供结果为 110 的 `Task<int>`。

```text
LoadPriceAsync          AddDeliveryFeeAsync          GetTotalAsync
    120 ──直接传值──→      120 + 10 ──直接传值──→       130 - 20
                                                          ↓
                                            向外部提供 Task<int>，结果是 110
```

**中间两层可以直接传递整数，不必先返回任务、再从任务里取出整数。**原来的三个方法仍然分工清楚，业务计算一项也没少，运行时省下了这两处任务相关的处理。

这套内部调用方式在设计资料中称为 AsyncCall。它既能传递计算结果，也能报告这次调用需要暂停。更细的约定可参见 [Runtime Async 规范](https://github.com/dotnet/runtime/blob/main/docs/design/specs/runtime-async.md)与[代码生成说明](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/runtime-async-codegen.md)。

### 文件还没读完时，先保存什么，再恢复什么

现在令 `cacheHit` 为 `false`，并假设文件读取没有立即完成。

此时价格还不知道，加运费和减优惠当然也做不了。Runtime Async 必须记住这几个方法剩下的工作，才能让线程先离开。

先不管内部类型名称，把要记住的内容列出来：

| 方法 | 等待结束后还要做什么 | 恢复时需要哪些信息 |
| --- | --- | --- |
| `LoadPriceAsync` | 取得文件文本，再调用 `int.Parse` | 从哪里继续、怎样取得读取结果 |
| `AddDeliveryFeeAsync` | 把读到的价格加上运费 | 从哪里继续、运费是多少、去哪里取得价格 |
| `GetTotalAsync` | 把含运费的金额减去 20 | 从哪里继续、去哪里取得上一层的金额 |

运行时会为需要恢复的执行保存相应信息，并把先后关系连起来。这些保存下来的恢复信息，就是这里所说的 **continuation**。它可以包含恢复位置、仍然需要的值，以及结果和异常该交到哪里。具体保存哪些字段，由 JIT 根据代码决定；例如已经能直接写进机器代码的常量，就不必再保存一份。

这个过程从里往外发生：读取没有完成，`LoadPriceAsync` 报告自己需要暂停；加运费的方法也保存后续计算所需的信息；最外层再保存减优惠这一步。随后这些方法退出当前调用栈，外部拿到一个尚未完成的 `Task<int>`。原线程可以去做别的工作。

文件读取完成后，运行时按之前记下的关系恢复执行。假设文本是 `"120"`，过程就是：

```text
读取完成，文本为 "120"
    ↓
继续 LoadPriceAsync：解析成整数 120
    ↓ 把结果交给下一步
继续 AddDeliveryFeeAsync：取得运费 10，算出 130
    ↓ 把结果交给下一步
继续 GetTotalAsync：减去 20，算出 110
    ↓
外部拿到的 Task<int> 完成，结果为 110
```

这里仍然需要保存现场，因为运费和恢复位置不能在等待期间丢掉。但在符合条件的这条调用链中，运行时可以直接安排各步恢复和结果传递，省去为每个中间方法另外提供一个任务的需要。

对照传统方式看，差别就更具体了：

```text
传统方式：内层任务完成 → 恢复加运费的状态机 → 该层任务完成
                     → 恢复减优惠的状态机 → 最外层任务完成

Runtime Async：按照保存的恢复关系继续计算，把结果逐步交给后续代码
                     → 完成外部需要的任务
```

两种方式都能让线程离开等待现场。Runtime Async 改进的是保存现场、恢复执行和方法之间传递结果的安排。文件读取本身仍需完成，也仍可能有底层 I/O 所需的对象和资源。

### 为什么有些 Task 仍然必须保留

上面的例子里，中间任务只是拿来立即 `await`，没有其他用途。再看下面的用法，假设 `pendingRequests` 是其他代码也会读取的任务列表：

```csharp
Task<int> priceTask = LoadPriceAsync(cacheHit);
pendingRequests.Add(priceTask);
int price = await priceTask;
```

现在，列表的使用者需要拿到这个任务，可能查看它有没有完成，也可能稍后等待它。只给当前方法一个整数，就无法满足列表使用者的需要。因此，运行时仍需提供这个 `Task<int>` 对象。

所以，判断中间任务能否省掉，要看程序是否需要使用任务对象本身。“只要最后的价格”与“还要拿着这次查询的任务，在别处观察它”，是两种不同需求。

这也解释了为什么 Runtime Async 不要求把所有 `ValueTask<T>` 改成 `Task<T>`。内部直接调用能省掉一些任务；真正需要向外部返回一个异步结果时，结果是否经常同步完成、能否复用底层等待对象等因素仍然影响返回类型的选择。

### 读到错误内容时，异常怎样传到最外面

继续使用同一个例子。假设文件内容是 `"abc"`，读取结束后，`LoadPriceAsync` 的 `int.Parse` 抛出 `FormatException`。

传统状态机会捕获这个方法没有处理的异常，把它记入 `LoadPriceAsync` 返回的任务。然后，加运费的方法执行 `await` 时发现任务失败，把异常重新抛出；它自己的状态机又捕获异常，记入自己的任务。减优惠的方法再重复一次。

```text
LoadPriceAsync 解析失败
    → 记录到读取价格的任务
    → AddDeliveryFeeAsync 的 await 重新抛出
    → 记录到含运费金额的任务
    → GetTotalAsync 的 await 再次抛出
    → 记录到最终任务
```

这几层业务代码都没有写 `catch`，它们并不打算处理错误。重复的捕获和记录，是为了通过各自的任务把失败传出去。

Runtime Async 已经掌握后续有哪些计算、哪些位置需要处理异常。恢复读取价格的方法时发现错误，就可以沿保存的恢复关系向外查找。在本例中，加运费和减优惠都没有异常处理代码，于是可以跳过这些中间步骤，直接让外部等待的任务失败。

如果开发者在加运费的方法里写了处理该异常的 `catch`，那段代码就必须执行；需要执行的 `finally` 也必须保留。运行时省掉的是单纯为了中转失败而做的工作。

实现中的 [DispatchContinuations 和 UnwindToPossibleHandler](https://github.com/dotnet/runtime/blob/main/src/coreclr/System.Private.CoreLib/src/System/Runtime/CompilerServices/AsyncHelpers.CoreCLR.cs) 对应的就是这个过程：恢复执行、遇到异常后寻找处理位置，或者完成最终任务的失败状态。若错误发生时整条调用尚未暂停，则可以沿当前调用栈传播，而不必走恢复调度这条路径。

### 为什么把这项工作交给 JIT，会有更多优化机会

回到三个价格方法。传统 C# 编译器在生成程序集时，已经为每个方法安排了状态字段、恢复分支和任务处理。JIT 接手后，需要在这套已经展开的代码里优化。

Runtime Async 让 JIT 更早看到“这里调用一个异步方法，随后等待它”这个关系。它生成机器代码时，可以一起决定：立即完成时怎样直接传值，暂停时保存哪些仍然需要的变量，恢复后怎样把结果交给下一步。

因此，它的作用可以从这个例子里直接观察：

| 执行情况 | 仍然要做的事 | 有机会减少的工作 |
| --- | --- | --- |
| 缓存命中，立即完成 | 120 加运费、再减优惠 | 创建中间任务、再从中读取结果 |
| 等待文件读取 | 保存恢复所需信息，读取结束后继续计算 | 各层分别通过任务安排恢复、传递结果 |
| 读取后解析失败 | 执行需要的异常处理，让外部知道失败 | 没有处理逻辑的层层抛出、捕获和记录 |

优化效果取决于实际调用是否走到这些路径。小型异步辅助方法很多时，方法之间的处理成本容易累积；若一次调用大部分时间都在等待远端服务，减少这些 CPU 和分配开销，也不一定让总等待时间明显缩短。

开发者写下的 `await`、异常处理和上下文规则继续有效。例如，`ConfigureAwait(false)` 仍控制恢复时是否回到捕获的上下文，不会因此自动禁止 `AsyncLocal<T>` 等执行上下文信息流动。

### 程序集和诊断工具也会受影响

既然 C# 编译器不再为适用的方法预先生成完整状态机，程序集里也就少了相应的生成类型、字段和 `MoveNext` 方法体。暂停与恢复的代码仍然需要，只是由运行时和 JIT 在后面安排。这是程序集能够变小的原因。

性能诊断的问题也可以用刚才的例子说明：文件读取恢复后，采样工具可能只看到正在执行 `int.Parse`，看不到早已退出当前线程调用栈的 `AddDeliveryFeeAsync` 和 `GetTotalAsync`。要知道这次解析属于哪条业务请求，还需要把恢复前后的调用关系连起来。

[新的异步分析事件流](https://github.com/dotnet/runtime/pull/127238)记录这些关系，并通过先在线程内缓冲、再批量提交等方式减少记录开销。工具可以据此补出逻辑上的异步调用链。后续 [PR #129043](https://github.com/dotnet/runtime/pull/129043) 也为传统状态机增加了支持，所以这项诊断能力并不只服务于启用 Runtime Async 的代码。

### 在 .NET 11 中怎样使用

截至本文核对日期，应用代码需要选择启用 Runtime Async。使用支持它的 .NET 11 SDK 和目标框架，在项目文件中加入：

```xml
<PropertyGroup>
  <Features>$(Features);runtime-async=on</Features>
</PropertyGroup>
```

这里保留原来的 `Features`，再追加开关。官方说明中，`net11.0` 项目不再需要为此设置 `EnablePreviewFeatures`。框架库已采用新方式编译，与自己的应用是否采用新方式是两件事：旧应用程序集不会因为换了运行时，就重新变成上述编译结果。参见 [官方 Runtime Async 说明](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/runtime)。

采用新方式的方法也可以调用旧库。旧方法仍按原有实现提供任务，运行时负责把它接入等待和恢复过程。因此不需要一次性重编所有依赖，但一条调用链能省掉多少中间工作，会受各层实现方式影响。

这一实现支持的返回类型是 `Task`、`Task<T>`、`ValueTask`、`ValueTask<T>`。`async void`、异步迭代器和带自定义 builder 的返回类型不在同一支持范围内，仍需按各自的编译实现理解。

验证效果时，可以沿本章的三个过程分别测：缓存命中、真实等待、异常失败。它们触发的工作不同，把三种情况混成一个平均值，很难看清收益来自哪里。源码仍可按业务职责拆成小方法，再由测量判断 Runtime Async 为这条调用链减少了多少开销。

相关专题：[Runtime Async 与 Union Type](../../CSharpGuide/net11-runtime-async/README.md)。

## 3. 边界检查：已经检查过的地方，不必再查一次

先看一次最普通的数组访问：

```csharp
int value = values[index];
```

这行代码执行前，需要确认 `index` 没有小于零，也没有达到数组长度。否则应当抛出异常。这样的判断就是边界检查，数组、字符串和 span 的索引访问都需要它。

但检查不一定要在每次访问时做。例如：

```csharp
for (int i = 0; i < values.Length; i++)
{
    total += values[i];
}
```

`i` 从零开始，只有小于数组长度时才进入循环。既然循环条件已经保证了索引合法，循环体里的 `values[i]` 就不必再查一遍。JIT 很早就能处理这种写法。.NET 11 继续解决的是其他一些本来也能确定不会越界、过去却没分析出来的情况。

### 排除了长度 0 和 1，就知道至少有两个元素

假设解析一段文本时，先处理空文本，再处理只有一个字符的情况：

```csharp
if (name.Length == 0)
    return false;

if (name.Length == 1)
    return false;

return name[0] == ':' && name[1] != ':';
```

能走到最后一行，长度就至少是 2。我们一眼能看出 `name[0]` 和 `name[1]` 都不会越界，JIT 也需要得出同样的结论。

过去的范围分析有一处欠缺：已知长度不可能为负，但遇到“长度不等于 0”时，没有充分利用它把最小值从 0 改成 1；再排除 1，也就没能继续得到“至少是 2”。.NET 11 补上了这种推理，列表模式生成的长度判断也能受益。[实现修改](https://github.com/dotnet/runtime/pull/121273)

这里利用的是区间两端的值。已知一个数在 0 到 10 之间，排除 0，可以把范围缩成 1 到 10；排除中间的 5，却不能用一个更小的连续区间表示剩余取值。这也是这项修改特意处理区间端点的原因。

### 第一次访问成功，也能替后面的访问提供依据

```csharp
static void ClearPair(int[] values, int index)
{
    values[index] = 0;
    index++;
    if (index < values.Length)
        values[index] = 0;
}
```

第一行赋值如果成功，原来的 `index` 就一定非负，而且小于数组长度。加一之后，再经过 `if` 检查，就同时知道新的 `index` 非负、没有达到数组末尾。第二次赋值需要的条件已经齐了。

以前，范围分析主要利用进入这段代码之前得到的信息，可能漏掉同一段代码刚刚检查出来的结果。.NET 11 会按执行顺序收集这些信息，因此能保留第一次访问的检查，去掉第二次多余的检查。[实现修改](https://github.com/dotnet/runtime/pull/121527)

### 为什么常看到 `(uint)index < (uint)length`

性能敏感的代码里经常这样判断索引：

```csharp
static int ReadOrDefault(ReadOnlySpan<int> span, int index)
{
    if ((uint)index < (uint)span.Length)
        return span[index];

    return 0;
}
```

在通常的非 checked 转换下，`-1` 转成 `uint` 是 `4294967295`。span 的长度不会有这么大，因此负索引无法通过比较；超过末尾的正索引同样无法通过。一个无符号比较就把两边都检查了。

.NET 11 改善了对这个条件的分析，特别是记住通过比较以后 `index` 一定非负。这样后续涉及索引的计算就能利用这个下界。[实现修改](https://github.com/dotnet/runtime/pull/125056)

当然，`index` 仍可能是零，所以单凭这个条件不能访问 `span[index - 1]`，还需要确认 `index > 0`。解析器向后看两个字符时也是一样：循环已经限制了当前索引，再确认 `index + 2` 没超出长度，就可以访问接下来的两个字符。.NET 11 也补强了这类分析。[向后查看字符的修改](https://github.com/dotnet/runtime/pull/124242)

### 算出来的索引，最大值也可以提前确定

编码器常用位运算计算查表位置，例如：

```csharp
int index = ((value & 0x03) << 4) | ((value & 0xF0) >> 4);
```

把它分开看就不复杂了：

- `value & 0x03` 只留下最低两位，左移四位后，最大值是 48。
- `(value & 0xF0) >> 4` 只留下另一组四位，最大值是 15。
- 两部分合起来只占最低六位，所以结果最大是 63。

如果目标表至少有 64 项，这个索引就不可能越界。旧分析已经认识其中的按位与和移位，.NET 11 又补上了按位或，才能把整条表达式分析完，省去查表时的检查。[实现修改](https://github.com/dotnet/runtime/pull/122263)

### 读最后四个字节，为什么过去还会检查三次

```csharp
using System.Buffers.Binary;

static bool TryReadTrailer(ReadOnlySpan<byte> packet, out uint trailer)
{
    if (packet.Length < 4)
    {
        trailer = 0;
        return false;
    }

    ReadOnlySpan<byte> lastFour = packet.Slice(packet.Length - 4);
    trailer = BinaryPrimitives.ReadUInt32LittleEndian(lastFour);
    return true;
}
```

开头已经确认有四个字节。可后面调用的两个方法各自也要保证安全：`Slice` 会检查起点是否合法，`ReadUInt32LittleEndian` 会检查输入有没有四个字节。于是同一件事，可能在三个地方分别检查。

要省掉后两次，JIT 得算清楚：长度至少是 4，所以 `Length - 4` 不会是负数，也不会超过原长度；切片剩下的长度则是 `Length - (Length - 4)`，刚好等于 4。

.NET 11 同时改进了这两处计算。JIT 把后面的检查化简以后，就只需保留开头那次 `Length < 4`。读取文件尾部字段、协议包尾部校验值时，都容易出现这种写法。[实现修改](https://github.com/dotnet/runtime/pull/127488)

### 连续读四项，可以用一次检查覆盖

```csharp
return values[0] + values[1] + values[2] + values[3];
```

只要数组有四项，这四次读取就都合法。在没有其他操作影响执行顺序的情况下，JIT 可以先检查最大索引 3，再省掉对 0、1、2 的单独检查。.NET 11 增加了合并这类检查的处理，也扩展了在 `return` 语句中生成快速版本的能力。[检查合并](https://github.com/dotnet/runtime/pull/127439)、[返回语句中的优化](https://github.com/dotnet/runtime/pull/124705)

这里对执行顺序的要求很实际。如果两次读取之间还写了日志、修改了对象，不能随便把后面的越界异常提前到这些操作之前。JIT 需要保留程序原本能观察到的行为。

### 循环里检查很多次，可以先判断整个范围

```csharp
static void FillPrefix(Span<int> values, int count)
{
    for (int i = 0; i < count; i++)
        values[i] = 1;
}
```

这个循环与本章开头不同：循环条件用的是 `count`，并没有保证 `count` 不大于 `values.Length`。因此，只看循环条件还不能去掉每次写入前的检查。

JIT 可以生成两份循环。先判断 `count` 是否落在合法范围内：如果是，就执行省去了逐项检查的版本；如果不是，就执行原来的版本。这叫循环克隆。

为什么还要保留原来的版本，而不直接抛异常？假设 `values` 有三项，`count` 是五。原代码会先把前三项写成 1，写第四项时才抛异常。如果改成循环前直接抛出，前三项就没有被修改，程序行为变了。

.NET 11 扩展了这种优化能识别的循环，包括部分使用 `i != end`、每次加一或减一的写法。`!=` 的起止值如果次序不对，还可能一直运行到整数绕回，所以 JIT 必须把这些情况送回一般版本处理。[实现修改](https://github.com/dotnet/runtime/pull/129268)

分块处理 span 也有类似的重复检查。循环已经判断剩下的数据够一个向量，加载向量时又判断一次；处理完一块、切掉一块以后，下轮还要继续。新的分析能更好地跟住每轮剩余长度，把加载时多做的检查去掉。[实现修改](https://github.com/dotnet/runtime/pull/127117)

### 同样的范围分析，还能去掉多余的溢出检查

```csharp
static byte ToSmallByte(uint value)
{
    if (value > 80)
        throw new ArgumentOutOfRangeException(nameof(value));
    return checked((byte)value);
}
```

走到最后一行，`value` 只可能在 0 到 80 之间，转成能容纳 0 到 255 的 `byte` 肯定不会溢出。`checked` 在源码里保留着，生成的机器代码却可以省掉它的溢出判断。.NET 11 将类似分析用在更多整数加减乘和窄化转换上。[整数运算](https://github.com/dotnet/runtime/pull/124147)、[类型转换](https://github.com/dotnet/runtime/pull/124184)

本章这些例子都可以继续使用数组、span 和标准读取方法。把检查写清楚，JIT 就有机会利用它们。若某段热点仍有重复检查，再查看生成的机器代码，确认它究竟没认出哪一步；通常不必一开始就换成指针来绕开检查。

## 4. 向量化：一次算多个值，再省掉多余的指令

假设有十六个整数，都需要加上同一个数。普通代码逐个做加法；SIMD 指令可以同时处理多个整数。128 位向量装得下四个 32 位整数，512 位向量则装得下十六个。

这些位置在文档里常叫 lane，下文直接称为元素。数据装进向量后，还可能需要准备常量、选择哪些元素要更新，以及合并最后的结果。.NET 11 的这一组改进，主要在减少这些操作。

### 十六个相同的常量，只存一份就够了

例如，对十六个整数分别执行 `x & 255`，计算时需要这样一组掩码：

```text
输入：[x0, x1, x2, ... , x15]
掩码：[255, 255, 255, ... , 255]
```

一种办法是在常量区放十六份 `255`，一次加载进向量；另一种办法是只放一份，让 CPU 读取后复制到每个元素的位置。后一种操作叫广播。

部分 AVX-512 指令还能在执行运算时顺便完成广播。十六个 32 位数原本占 64 字节，现在可以只存 4 字节。.NET 11 改进了广播形式的选择，让更多合适的运算使用这种写法。[实现修改](https://github.com/dotnet/runtime/pull/117700)

这项收益首先体现在常量数据更少、缓存占用更小。是否也让某个方法明显变快，要看原来的数据装载是不是瓶颈。

### 选择结果已经确定，就不必真的执行选择

向量选择可以理解为逐项执行 `condition ? a : b`。例如：

```text
A：    [10, 20, 30, 40]
B：    [ 1,  2,  3,  4]
选择 A：[是, 否, 是, 否]
结果： [10,  2, 30,  4]
```

如果条件全是“是”，结果就是 A，B 和选择操作都用不上。如果某一边全是零，有些选择又能改成更简单的按位与。.NET 11 把这些化简补到了更多 `ConditionalSelect` 和 `BlendVariable` 用法中。[实现修改](https://github.com/dotnet/runtime/pull/123146)

还有一种情况：先对所有元素算出新值，再把需要更新的位置挑出来，与旧值合并。支持掩码的指令可以边算边决定哪些位置更新，省去最后那次合并。

不过，掩码与运算必须按相同的元素宽度工作。一个掩码按 32 位整数划分位置，运算却按 64 位划分，就不能直接放到同一条指令里。这也是广播选择看似细小，却可能进一步影响指令合并的原因。

### 算完每个元素，还可能需要把结果合起来

求和时，四个元素分别算出的部分和，最后还要加成一个数；找最大值也要比较各个位置的候选结果。这一步叫归约。若最后又把整个向量写到栈上、逐项读取，前面虽然并行处理了，结尾仍然多做了一段标量工作。后面的 LINQ 章节会看到这类实际改进。

尾部数据也需要单独安排：十个元素，用一次处理四个的向量，要处理两组完整数据和剩下两项。短输入很可能主要花时间在这些准备和收尾上。

因此，使用 SIMD 的收益与数据长度、硬件以及算法都有关系。浮点求和还要考虑改变加法顺序后的舍入差异。标准库会处理这些细节，应用通常通过搜索、比较、复制和数值 API 获益；这里介绍的改进并不表示 JIT 已经能把任意 `for` 循环自动变成向量循环。

## 5. 写屏障与 GC：给对象字段赋值时，还做了什么

假设缓存对象 `Catalog` 已经活了很久，进入了老年代。现在创建一个新 `Item`，把它保存到缓存里：

```text
老年代 Catalog ──字段引用──→ 年轻代 Item
```

下一次只回收年轻代时，GC 必须知道 `Catalog` 还在使用这个 `Item`，否则就可能把仍然有用的对象当成垃圾。但如果每次都扫描整个老年代，分代回收节省的工作又做回来了。

.NET 会在需要的引用赋值处加上记录操作，告诉 GC 哪些位置值得检查。这部分代码叫写屏障。它为垃圾回收服务，与多线程里用来约束读写顺序的内存屏障是两回事。

### 写入时做标记，回收时再查看

运行时会用卡表等结构，把可能含有相关引用的堆区域标记出来。到年轻代回收时，GC 只需检查这些区域，就能找到老对象指向年轻对象的引用。

它通常不会每赋值一次，就往某个列表里追加一个精确的字段地址。记录可以粗一些：同一区域里的多个字段共用一个标记，回收时再扫描这片区域。这样赋值时少做工作，代价是 GC 要多看一些被一起标记的内容。

所以，写屏障的开销发生在引用写入处，GC 使用这些记录则是之后的事。即使这次赋值没有触发回收，也可能需要做标记。频繁更新对象字段或引用数组时，这段代码就值得优化。[GC 设计说明](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/garbage-collection.md)

### 数组赋值，除了索引，还要检查元素类型

```csharp
object[] values = new string[2];
values[0] = "ok";
// values[1] = new object(); // 执行时抛出 ArrayTypeMismatchException
```

变量写的是 `object[]`，实际数组却只能装字符串。运行时不能因为变量类型更宽，就让任意对象写进去。

因此，一次引用数组赋值可能要检查三件事：索引是否越界，值是否符合数组的实际元素类型，以及这次写入需要怎样通知 GC。以前这些工作被包在一个运行时辅助调用里，JIT 不容易分别处理。

.NET 11 把更多数组写入的辅助逻辑展开到 JIT 能分析的位置。比如数组的实际类型已经确定、待写值的类型也确定，类型检查就可能省掉；前面已经验证过长度，索引检查也可能省掉。仍有必要的写屏障则继续保留。[最初实现](https://github.com/dotnet/runtime/pull/117583)、[后续修复版本](https://github.com/dotnet/runtime/pull/126547)

### 复制结构体：引用照常处理，数值部分批量复制

一个结构体可能同时包含字符串引用和普通数值。复制到堆上的字段时，引用部分需要遵守 GC 的要求，普通数值则可以用较宽的加载和存储指令一次搬一段。

下面只是为了说明两类字段的区别，不代表所有结构体都按这个顺序布局：

```text
[引用 A][数值 1][数值 2][数值 3][数值 4][引用 B]
  ↑           中间这段可以批量复制           ↑
需要 GC 处理                           需要 GC 处理
```

.NET 11 移除了一个旧的特殊复制辅助方法，改用合适的引用写入操作，再单独复制普通数据。这样，中间的数据就能使用 SIMD 等更高效的复制方式，而不必跟着旧辅助方法逐段处理。[实现修改](https://github.com/dotnet/runtime/pull/128542)

该 PR 的混合结构体复制基准中，Intel Xeon Platinum 8573C 的结果从 31.152 ns 降到 2.724 ns，Apple M4 则从 1.4646 ns 降到 0.9574 ns。两者都是各平台主干与修改版的对照。x64 旧路径里较慢的复制操作被替换后，收益更大；Arm64 原来就没有同样重的成本，改善幅度便不同。

### 活得很久的关联关系，不必每次 Gen 0 回收都检查

`ConditionalWeakTable` 可以给一个对象附加另一个对象，例如给某个实例保存额外元数据。它的规则是：主对象还活着，关联的次对象就可以因此被保留；关联本身不应该把主对象永远留住。GC 通过 dependent handle 管理这种关系。

过去，这类句柄不会像其他句柄一样随对象变老。即使两端对象早已进入 Gen 2，每次 Gen 0 回收仍可能重新检查它。

假设程序里有十万个长期对象，都附着一份元数据。另一个模块频繁创建短命对象，持续触发 Gen 0 回收。这十万个老关系虽然没有变化，却跟着被反复检查，平白增加了年轻代回收的工作。

.NET 11 让 dependent handle 也能逐渐变老，年轻代回收可以跳过不相关的老句柄。以后关系变化、需要重新按较年轻状态处理时，再调整回来。[实现修改](https://github.com/dotnet/runtime/pull/78746)

### GC 自己也会排序

整理堆时，GC 需要安排存活对象搬到哪里。它会整理存活对象的地址，把相邻的存活对象归成区段，其中就涉及地址列表排序。

.NET 11 为 vxsort 增加了 Arm64 Neon 实现，较大的地址列表可以使用向量化排序。[实现修改](https://github.com/dotnet/runtime/pull/110692) 这项工作发生在回收器内部；前面的修改减少写入和扫描成本，这项则让已经需要执行的回收步骤更快。

## 6. 运行时知识与冻结数据：哪些信息可以让 JIT 少做工作

### 同一个调用目标，不必在循环里反复查找

假设代码在同一个对象上调用一百次泛型虚方法 `Process<string>()`。除了方法本身的工作，运行时还可能需要查出：这个对象的实际类型，对应哪个 `Process<string>` 实现。

如果每次查到的都是同一个入口，理想的执行过程就是：

```text
先查到 Process<string> 的入口
然后调用这个入口一百次
```

但是 JIT 不能随便把一个调用移到循环外。普通方法可能改变对象、读取不断变化的数据，或者抛异常。它必须知道，负责查找入口的辅助方法究竟会做什么。

.NET 11 更精确地描述了这些辅助方法的副作用和可能抛出的异常，JIT 才能在适用情况下复用查找结果，或者把查找移出循环。业务方法仍然执行一百次，省掉的是反复寻找入口的工作。[实现修改](https://github.com/dotnet/runtime/pull/122017)

异常也会限制移动位置。比如循环一次都不执行时，本来不会检查空引用；如果把查找无条件搬到循环前，却因此抛了异常，就改错了。知道辅助方法可能抛哪种异常，正是为了避免这种改变。

### 被内联的方法，也应该留下运行记录

PGO 根据程序实际怎样运行来优化热点。如果一个小方法总被内联到调用方，它自己的运行情况就可能没有被完整记录下来，后面需要优化时反而缺少资料。

.NET 11 允许在一些同时进行优化和插桩的编译过程中，也为被内联的代码加入记录。这样，内联以后发生的调用等信息仍能被收集，后续编译可以继续利用。[实现修改](https://github.com/dotnet/runtime/pull/119658)

### readonly、冻结集合和冻结对象堆，是三件不同的事

先看最常见的一种：

```csharp
static readonly int[] Codes = [10, 20, 30];
```

`readonly` 限制的是字段能在哪里被赋值。数组里的 `Codes[0]` 仍然可以修改，所以 JIT 不能只看见 `readonly`，就把读取第一项直接替换成常量 10。

`FrozenDictionary` 则是建好后不再增删改、适合反复查询的集合。它可以在构造时花些时间选择合适的存储方式，让以后的读取更快。它与普通字典的区别在集合实现，不在 GC 把它放在哪里。

FOH（Frozen Object Heap，冻结对象堆）说的才是运行时的存储区域。它用于某些由运行时管理、不移动且长期保留的对象。普通对象可能在 GC 整理时换地址，机器代码不能任意把当时的地址写死；运行时确认对象地址稳定后，就能采用更直接的引用方式。

但地址稳定，也不自动等于所有字段都不变。前者让 JIT 知道“以后还可以用这个地址”，后者才让它有机会把字段读取提前算成常量。两种优化需要的条件不同。

| 写法或机制 | 主要解决什么问题 |
| --- | --- |
| `readonly` 字段 | 限制字段重新赋值 |
| 冻结集合 | 为构造后反复查询选择合适的数据结构 |
| 冻结对象堆 | 由运行时管理特殊对象的地址和生命周期 |

FOH 在早期版本就已有相关工作，可以查阅[跟踪记录](https://github.com/dotnet/runtime/issues/76151)。原文这一小节着重展开的 .NET 11 改动，是前面的辅助方法信息和 PGO；FOH 是理解标题所需的背景。

.NET 11 也优化了 `ToFrozenDictionary` 的构造过程：源集合能提供数量时，先给中间字典准备足够容量，减少扩容。这里的“冻结”仍是集合含义，并没有把它迁进 FOH。[实现修改](https://github.com/dotnet/runtime/pull/128300)

## 7. 多线程：减少排队、唤醒和等待时的额外工作

### 线程刚醒来，队列可能已经空了

假设线程池队列只剩两个工作项，几个线程都判断需要更多人来处理，于是发出唤醒请求。等新线程真正开始运行，工作早被其他线程取走，它们检查一下队列，又进入等待。

这几次唤醒没有完成业务，却动用了信号量和系统调度，还读写了一些共享状态。小工作项很多时，这些零碎操作会占去不少 CPU。

.NET 11 减少了这类无效唤醒：控制工作线程请求，并在请求前确认队列确实还有工作。线程池向控制器汇报状态的频率也从每个工作项一次，改成每个调度时间片一次；同时删掉部分不必要的屏障和共享状态更新，缩短一些自旋等待。[线程池修改](https://github.com/dotnet/runtime/pull/122726)

所以，这组改进主要影响大量短工作项之间的调度成本。一个工作项本身算上几秒钟，通常不会因为少了这点调度工作就明显变快。

### Monitor.Wait 少查一张表

一个线程调用 `Monitor.Wait` 等待另一个线程发信号，运行时需要找到这把锁对应的条件对象，用它管理等待者。旧实现通过 `ConditionalWeakTable` 保存锁与条件对象的关联。

.NET 11 让锁直接关联条件对象，省去那次表查询，也减少建立关联时的分配和竞争。[实现修改](https://github.com/dotnet/runtime/pull/129083) `Task.Wait` 等调用在某些路径上也会用到这些等待设施，因此即使业务没有直接写 `Monitor.Wait`，仍可能受益。这次调整没有为公开的 `Lock` 类型新增 Wait/Pulse API。

### 已经有顺序保证的地方，少加一层限制

多个线程读写数据时，需要约束一些操作的先后顺序。例如，先把对象内容写好，再把引用交给另一个线程；读方看到引用后，应当能读到已经初始化的内容。

锁、原子操作和特定读写方式都可能提供这些保证。如果一段库代码已经靠它们保证正确性，再加 `volatile` 有时只是重复约束。线程执行的指令可能变多，编译器也可能因此少做一些优化。

.NET 11 检查了库中的一批字段，移除那些确实不需要的 `volatile`。判断依据是每个字段怎样发布、怎样读取，以及是否已经受锁或原子操作保护。[实现修改](https://github.com/dotnet/runtime/pull/125274)

CLR 内部哈希表还把部分完整内存屏障换成了更有针对性的 acquire/release 操作。比如写方先准备值，再发布键；读方确认键后再读值。满足这个顺序，就不一定需要约束所有方向的读写。[实现修改](https://github.com/dotnet/runtime/pull/125259)

### 哈希表扩容以后，旧数组要等读者用完

写线程扩容时，可以先建好新桶数组，再把表指向新数组。但已经开始查询的读线程可能仍拿着旧数组，旧内存不能立即释放。

.NET 11 在部分 CLR 内部表上采用基于 epoch 的延迟回收：先记下哪些读者可能还在用旧数据，等这些读者退出，再释放旧桶。这样可以减少读者为了保护旧数组而进行的 GC 模式切换。[实现修改](https://github.com/dotnet/runtime/pull/124822)

这里处理的是运行时自己的表。应用中的普通 `Dictionary` 仍然需要遵守原有并发使用规则。

### 操作提前完成，Task.Delay 的定时器却还在等

下面是常见的手写超时方式：

```csharp
Task completed = await Task.WhenAny(operation, Task.Delay(timeout));
```

如果 `operation` 很快完成，`WhenAny` 会返回，但另一边的 `Task.Delay` 并不会自动结束。它的定时器仍然要等到超时时间才到期。

假设每次设置几分钟超时，实际操作却只要几十毫秒，请求量一大，尚未到期的定时器就会积累起来。它们最终会结束，不是永远泄漏，但在到期之前仍占用资源。

SDK 新增的 [CA2027 分析器](https://github.com/dotnet/sdk/pull/51452) 会提示一部分这种没有取消机制的写法。只需要限制等待时间时，可以使用已有的 `WaitAsync`，由它处理等待所需的定时和清理：

```csharp
await operation.WaitAsync(TimeSpan.FromSeconds(3), cancellationToken);
```

这里最多等三秒，超时会抛出 `TimeoutException`。如果还要求三秒后终止底层 I/O，需要另外把取消信号传给那个操作；结束等待并不会自动停止被等待的工作。[API 说明](https://learn.microsoft.com/en-us/dotnet/api/system.threading.tasks.task.waitasync?view=net-10.0)

## 8. 数值计算：一次处理更多位，少做重复计算

### BigInteger 怎么存一个放不进 long 的整数

先把“原生位宽”“数位块”这些名字放一放。`BigInteger` 面对的第一个问题很简单：数字太大，一个普通整数变量放不下，要怎么办？

办法是把一个大数分成几段，用一组整数保存。计算时再把这些段当成同一个数处理。

#### 先用十进制看“分段”是什么意思

比如 `12345678`，可以每两位分一组，也可以每四位分一组：

```text
每两位一组： [12] [34] [56] [78]     四组
每四位一组： [1234] [5678]          两组
```

两种写法表示的都是同一个整数，只是每组装的位数不同。它们不是四个或两个互不相关的数；每组所在的位置也决定了它在整个数里的大小。

做加法时，就像手算竖式，需要从右往左处理进位。以 `1299 + 1` 为例：

```text
每两位一组： [12] [99] + [00] [01]

先算右边：99 + 1 = 100
右边只能放两位，所以留下 00，向左进 1
再算左边：12 + 1 = 13
结果：    [13] [00]，也就是 1300
```

如果每组能放四位，`1299` 就能放在一组里，直接算出 `1300`，不用跨组传递这次进位。

**每组装得更多，同样大的数就需要更少的组，运算时逐组处理的次数也可能更少。**

#### 对应到 .NET，就是从 uint 换成 nuint

实际的 `BigInteger` 按二进制分组，不是按上面的十进制位数分组。每一组通常叫 limb，这里继续称为“块”。

过去内部用 `uint` 保存块，一块是 32 位。.NET 11 改用 `nuint`，它的大小随进程位数变化：64 位进程里是 64 位，32 位进程里仍是 32 位。[实现修改](https://github.com/dotnet/runtime/pull/125799)

因此，一个需要 256 位表示的大整数，在 64 位进程中会有这样的区别：

| 存储方式 | 每块能放多少位 | 需要多少块 |
| --- | --- | --- |
| 32 位块 | 32 位 | 8 块 |
| 64 位块 | 64 位 | 4 块 |

64 位 CPU 本来就能直接做很多 64 位整数运算。以前一段需要循环八次的逐块处理，现在可能只需要四次，读取块、更新位置和传递进位的次数也跟着减少。

乘法也会受影响。最直接的大数乘法，要让左边的每块与右边的每块相乘。八块乘八块有 64 对，四块乘四块只有 16 对。不过，64 位块相乘会产生更宽的中间结果，还需要处理进位，所以不能单凭这两个数量就断言快四倍。

这项变化发生在 `BigInteger` 内部。业务仍然写 `a + b`、`a * b`，不需要自己拆块。这里讨论的是需要多块存储的大数；较小的 `BigInteger` 本来就有更简单的表示，32 位进程也没有这次块宽翻倍的收益。

### ModPow 怎么算：先减少乘法，再降低取余数的成本

`BigInteger.ModPow(a, e, m)` 做的是：

```text
a 的 e 次方，除以 m 后的余数
```

例如 `ModPow(7, 15, 11)`，就是 `7¹⁵ % 11`。调用方只要余数，没必要先得到完整的 `7¹⁵`。

要理解这里的优化，先跟着算出这个余数。下面都用正整数，最终结果是 10。

#### 算到一半就取余数，结果不会变

有一个很有用的规律：乘法的中间结果先取余数，再继续相乘，最终余数不变。

例如计算 `7⁴ % 11`：

```text
先算完整结果：7⁴ = 2401，2401 % 11 = 3

边算边取余数：
7² = 49，49 % 11 = 5
7⁴ 的余数可以继续用 5 × 5 来算
5 × 5 = 25，25 % 11 = 3
```

因为 `49 = 4 × 11 + 5`，多出来的那部分本来就是 11 的倍数，继续做整数乘法后也不会影响最终除以 11 的余数。

这让每一步结束时的结果都缩回 0 到 10，而不用保留越来越大的幂。对真正的大数而言，即使模数也很大，仍然比放任幂的位数持续增长便宜得多。

不过，边乘边取余数只是控制了数字大小，还可以进一步减少乘法次数。

#### 算 7¹⁵，不必把 7 连乘十四次

平方能快速得到更高的幂：

| 要算的幂 | 利用前面的结果 | 除以 11 的余数 |
| --- | --- | --- |
| `7²` | `7 × 7 = 49` | 5 |
| `7⁴` | 用上一步的余数算 `5 × 5 = 25` | 3 |
| `7⁸` | 再算 `3 × 3 = 9` | 9 |

因为 `15 = 8 + 4 + 2 + 1`，所以：

```text
7¹⁵ = 7⁸ × 7⁴ × 7² × 7
```

现在用已经得到的余数相乘：

```text
9 × 3 = 27，取余后是 5
5 × 5 = 25，取余后是 3
3 × 7 = 21，取余后是 10
```

三次平方，加上三次组合乘法，共六次乘法，就得到了答案。朴素地从 7 开始不断乘 7，则需要十四次。

这就是利用指数的二进制来算幂的基本思路：15 的二进制是 `1111`，对应需要的 `8、4、2、1` 四个幂。这种平方再相乘的方法早已存在，下面的滑动窗口是在它基础上继续减少工作。

#### 滑动窗口：指数里的几位，可以合起来处理

仍然用二进制 `1111`，这次用两个二进制位作为窗口来演示：

```text
逐位看：1 1 1 1
分组看：11 | 11
```

二进制 `11` 是十进制 3。既然要按组处理，就先准备 `7³ % 11`：

```text
7² % 11 = 5
7³ % 11 = (5 × 7) % 11 = 2
```

处理第一组 `11`，当前指数是 3，结果就使用这个预先算好的 2。

再读入后面两位，相当于把当前指数左移两位，然后加上新的一组：

```text
指数：3 → 3 × 4 + 3 = 15
幂：  7³ → (7³)⁴ × 7³ = 7¹⁵
```

所以接下来只需要平方两次，再乘一次预先准备的 `7³`：

```text
当前余数 2
平方一次：2 × 2 = 4                 对应 7⁶
再平方：  4 × 4 = 16，取余后是 5    对应 7¹²
乘预备值：5 × 2 = 10               对应 7¹⁵
```

准备阶段两次乘法，后面三次，总共五次，比前面的六次又少了一次。这个小例子主要用来说明过程；实际算法会根据指数长度选择窗口大小，并决定怎样划分各组，不是把所有指数都固定切成两位。

对很长的指数，准备好的小幂可以多次复用，这才更有机会抵消预计算的成本。.NET 11 的 `ModPow` 改进包含了这种滑动窗口处理。

#### Montgomery：每次乘完取余数，也可以换一种更便宜的算法

前面为了方便理解，一直写成“乘完以后 `% 11`”。但大整数除法和取余数本身也很贵。如果做成百上千次模乘，每次都执行一般的大整数除法，花费就会积累起来。

Montgomery 方法专门优化这部分。它先把数转换成另一种表示，在这种表示下完成一连串模乘，最后再转回普通数。内部可以主要使用乘法、加法、取低位和移位，避开反复做一般除法。

“换一种表示”听起来抽象，可以用一个小例子看清它怎样工作。下面单独计算 `7 × 3 % 11`，普通结果应该是 10。

选一个比 11 大的二的幂，这里用 16。先把每个输入改记为“乘以 16 后，再对 11 取余数”：

```text
原来的 7，改记成 (7 × 16) % 11 = 2
原来的 3，改记成 (3 × 16) % 11 = 4
```

现在不能简单地把 `2 × 4 = 8` 当成结果，因为两边各带了一份 16，相乘以后带了两份，而我们希望结果继续只带一份。Montgomery 乘法会处理掉多出来的这一份。

这个例子可以这样做：

```text
先相乘：                 2 × 4 = 8
给它加上某个 11 的倍数： 8 + 8 × 11 = 96
然后除以 16：           96 / 16 = 6
```

加上 11 的倍数不会改变对 11 的余数；特意把结果补成 16 的倍数，就能用右移四位完成这次除法。这里除掉的 16，正好与前面特殊表示中多出来的那份相配。

得到的 6 仍然是特殊表示。它代表普通结果 10，因为：

```text
(10 × 16) % 11 = 6
```

最后还原时，也可以用同样的办法去掉剩下的那份 16：给 6 加上 14 个 11，得到 160，再除以 16，就得到普通结果 10。

真实实现不会试着加一个、两个、三个 11，直到凑成 16 的倍数。模数固定后，可以先算好辅助常量，再根据低位算出要补的倍数。完整算法还包含必要时减去一次模数等收尾步骤；上面的数字只展示最关键的过程。

若只算一次 `7 × 3`，先转换再转换回来很不划算。`ModPow` 却要在同一个模数下反复相乘，进入特殊表示一次，就能连续完成后面的计算，最后统一还原。这样才容易把准备成本摊薄。

.NET 11 将 Montgomery 用于适用的奇数模数。原因与选用二的幂有关：模数为奇数，才能满足这种转换需要的互素条件。滑动窗口减少的是乘法次数，Montgomery 降低的是每次模乘的成本，两项改进可以一起使用。[ModPow 实现改进](https://github.com/dotnet/runtime/pull/125799)

### 普通大数乘法：为什么多做加减，反而能少做乘法

Toom-Cook 讨论的是另一个问题：计算两个大整数的乘积时，怎样少做一些较小整数的乘法。它不要求计算余数，因此与刚才的 `ModPow` 分开理解更容易。

先看熟悉的 `12 × 34`。把两位数拆开，按竖式展开需要四个乘积：

```text
12 × 34
= (10 + 2) × (30 + 4)
= 300 + 40 + 60 + 8
= 408
```

其中分别用了 `1 × 3`、`1 × 4`、`2 × 3`、`2 × 4` 四次小乘法。

但中间的两项只需要知道合计，不必分别算出来。可以改算：

```text
高位乘积：1 × 3 = 3
低位乘积：2 × 4 = 8
相加后乘：(1 + 2) × (3 + 4) = 21
```

最后这项展开后包含了四个小乘积。减去已经知道的高位乘积 3 和低位乘积 8，就剩中间两项之和：

```text
21 - 3 - 8 = 10
最终结果：3 × 100 + 10 × 10 + 8 = 408
```

这样只做了三次小乘法，多做了几次加减。对两位数不值得折腾；但如果每一“位”其实是一大块整数，乘法远比加减贵，节省一次乘法就可能划算。

这里统计的是块与块的乘法。最后乘 10、乘 100，是把结果放回相应数位；实际按二进制分块时，对应的是移位，不需要再执行同样的大数乘法。

上面演示的是 Karatsuba，也常称 Toom-2 的思路，不是说 .NET 11 才发明或首次采用它。Toom-3 再把两边各拆成三块：直接展开需要九次块乘法，它通过组合这些块，用五次约三分之一规模的乘法，加上额外的加减和重组得到结果。[Toom-Cook 实现](https://github.com/dotnet/runtime/pull/112876)

输入越大，少做乘法越有价值；输入小时，拆分和重组反而可能更贵。因此实现会按大小选择算法，相关 PR 也记录过部分小输入略慢的情况。各 PR 的测试来自不同开发阶段，不能把它们当成同一套版本对照。

把这几个改进放回各自的位置，就容易区分了：

| 改进 | 省掉的主要工作 |
| --- | --- |
| 32 位块改成原生位宽块 | 处理同样大小的数时，少循环、少传递几次进位 |
| 滑动窗口 | 求幂时，减少部分乘法次数 |
| Montgomery | 反复模乘时，减少一般大整数除法 |
| Toom-Cook | 大整数相乘时，用额外加减换取较少的子乘法 |

### UTF-8 输入可以直接解析，不必先建字符串

从网络或文件拿到的文本通常是 UTF-8 字节。过去解析大整数，调用方可能先把字节转成字符串，再交给 `BigInteger.Parse`。

.NET 11 为 `BigInteger` 和 `Complex` 加入直接处理 UTF-8 的解析与格式化 API，可以省去这一步。[实现修改](https://github.com/dotnet/runtime/pull/117745)

```csharp
using System.Globalization;
using System.Numerics;
using System.Text;

static BigInteger ParseViaString(ReadOnlySpan<byte> utf8) =>
    BigInteger.Parse(Encoding.UTF8.GetString(utf8), CultureInfo.InvariantCulture);

static BigInteger ParseUtf8(ReadOnlySpan<byte> utf8) =>
    BigInteger.Parse(utf8, CultureInfo.InvariantCulture);
```

第二个方法直接读取现有字节，少了一个临时字符串和一次转码。解析后的大整数仍然需要自己的内部存储；省掉的是输入在解析前多绕的那一步。两条路径都指定相同文化信息，以便采用相同的数字解释规则。[方法签名](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Runtime.Numerics/src/System/Numerics/BigInteger.cs)

格式化也一样。如果接下来要把结果发到网络，直接写入字节缓冲，就不用先生成 UTF-16 文本，再编码成 UTF-8。要获得这项收益，需要调用新重载；原有代码里的 `Encoding.UTF8.GetString` 不会自动消失。

### 浮点数的批量运算，还要处理特殊值

.NET 11 为 [Matrix4x4 的行列式](https://github.com/dotnet/runtime/pull/123954)增加 SSE 实现，也让 [TensorPrimitives.Asin](https://github.com/dotnet/runtime/pull/126052)使用向量化计算。前者同时处理矩阵中的一些乘加项，后者一次为多个输入求反正弦。

有些运算看起来只是改几位，实际还要照顾浮点数的特殊情况。`BitIncrement` 求的是向正方向紧邻的下一个可表示浮点数，不是加一。正常正数的位模式可以向一个方向调整，负数要反过来；正负零、无穷和 NaN 则需要专门处理。新的向量实现把这些判断和选择一起处理，让多个输入共享同一批指令。[实现修改](https://github.com/dotnet/runtime/pull/123610)

`Half.CompareTo` 过去会依次判断小于、大于和相等。如果三个操作各自处理一遍 NaN 和零，相同的判断就做了好几次。现在先集中处理特殊情况，再比较；在支持的 x64 路径上，还能把 `Half` 无损转换成 `float`，使用更便宜的硬件比较。[实现修改](https://github.com/dotnet/runtime/pull/131297)

也有更直接的修复：`TensorPrimitives.Round` 在 `digits == 0` 时已经做完一遍舍入，却因为少了 `return`，继续执行后面的处理。补上返回，就少遍历一次输入和输出。[实现修改](https://github.com/dotnet/runtime/pull/124280)

### Guid 少走一层文件读取，Shuffle 少判断一次

Linux 上，`Guid.NewGuid()` 改用可用的 `getrandom()`，减少通过 `/dev/urandom` 文件描述符读取的开销。[实现修改](https://github.com/dotnet/runtime/pull/123540) PR 早期的约十倍结果还包含后来撤掉的批量缓存实验，最终保留的实现不能使用那组数字。

`Random.Shuffle` 的修改更小：去掉了“随机选中的位置是不是自己”的判断。[实现修改](https://github.com/dotnet/runtime/pull/119890)

自己和自己交换不会改变数据。如果元素很小，做一次交换很便宜；为了偶尔省掉这次交换，却每一轮都执行一个不容易预测的分支，反而可能更贵。因此，新实现直接交换，让正常循环少做一次判断。

## 9. 搜索与比较：先跳过明显不可能匹配的内容

### 正则先找哪里值得尝试

假设要在一大段文本中找 `error` 或 `warning`。可以先找字母 `e`、`w`，找到后再检查后面的字符；也可以直接搜索两个完整单词。

第一种搜索简单，但文本里如果到处都是 `e`，就会找到大量最后匹配失败的位置。第二种一次检查的信息更多，可能少做许多失败尝试。如果首字母本来就很罕见，第一种又可能已经足够好。

.NET 11 利用字符出现频率来选择部分正则的前缀搜索方式，在适用的区分大小写模式中决定使用字符集合搜索，还是 `SearchValues<string>` 的多字符串搜索。[实现修改](https://github.com/dotnet/runtime/pull/124736)

正则优化后还会再做一轮化简。前面的处理可能重新组织了分支，才露出原先没发现的公共部分。最后再检查一次，就可能提取公共前缀，避免失败后又把同一段输入扫描一遍。[实现修改](https://github.com/dotnet/runtime/pull/125289)

### 长度已经不对，就不用再比较字符

```regex
\A[A-Z]{6}\z
```

这个模式要求整个输入恰好是六个大写字母。传进来七个字符，内容再符合也不可能匹配。先看长度，就能直接返回失败。

.NET 11 为这类固定长度、两端限定的模式增加了提前判断，用于编译型和源生成型正则。[实现修改](https://github.com/dotnet/runtime/pull/120916)

这里用的是 `\A` 和 `\z`，表示整个输入的绝对开头和结尾。`$` 对末尾换行的处理不同，开启多行模式的 `^` 也可能匹配行首，所以不能把所有看起来有首尾符号的模式都按同一规则处理。

### 有些回溯注定失败，可以直接跳过

再看 `\b\w+q\b`：先匹配单词字符，再匹配一个 `q`，后面必须是单词边界。

`\w+` 会尽量吃掉整段单词。之后寻找最后的 `q` 时，通常需要往回退。但如果把 `q` 放在单词中间，它后面仍是单词字符，最后的 `\b` 肯定不成立。只有单词末尾的位置还有可能成功。

.NET 11 能识别这种关系，直接检查最后一个可能的位置，省去逐次向前回退的搜索。[实现修改](https://github.com/dotnet/runtime/pull/125636)

编译型正则还补上了两个源生成器已有的优化：几条分支以不同字符开头时，按首字符直接选择分支；比较区分大小写的反向引用时，使用 `SequenceEqual` 比较之前捕获的文本。[分支选择](https://github.com/dotnet/runtime/pull/122959)、[反向引用比较](https://github.com/dotnet/runtime/pull/123914)

### Guid 数组相等，可以直接比较数据

比较两个 `Guid` 序列时，原来的通用结构体处理方式可能逐项调用相等判断。`Guid` 的值相等可以由其位表示判断，因此能改用已经优化的内存比较，包括展开和向量比较。

.NET 11 将 `Guid`、`Int128`、`UInt128` 加入这种处理，使相关 `SequenceEqual` 调用受益。[实现修改](https://github.com/dotnet/runtime/pull/130644)

运行时需要对具体类型确认这一点。任意结构体可能包含填充字节，也可能自定义相等规则，不能仅凭“占用固定大小内存”就直接比较全部字节。

### Split 花了不少时间在找分隔符

一长段日志里可能很久才出现一个逗号。`Split` 在生成结果字符串之前，先要找到这些逗号。如果一整块没有逗号，就应尽快跳过，没必要继续算具体位置。

.NET 11 优化了常见单字符分隔符的搜索。对 ASCII 分隔符，可以先批量筛掉没有匹配的大段内容，再对可能命中的部分精确查找。[实现修改](https://github.com/dotnet/runtime/pull/125379) 最后生成各段字符串的分配仍然存在。

Arm64 上还改进了从向量比较结果中寻找位置的步骤。向量比较能同时指出哪些元素命中，接下来要把它转成“第一个在第几项”“一共命中几项”。过去一些实现先生成完整的标量位掩码，多做了转换；新实现改进了计数和索引查找的指令生成。[实现修改](https://github.com/dotnet/runtime/pull/126678)

### 排序时，让结构体比较器一直保持结构体

```csharp
readonly struct DescendingIntComparer : IComparer<int>
{
    public int Compare(int x, int y) => y.CompareTo(x);
}
```

这个比较器很小，也没有需要单独保存的状态。`Span<T>.Sort` 的泛型入口本来允许直接传入它，可内部实现若又把它装箱成 `IComparer<int>`，既分配了对象，每次比较也重新变成接口调用。

.NET 11 让排序内部继续使用具体的泛型比较器类型，避免这次装箱，并让 JIT 有机会把 `Compare` 内联进排序循环。[实现修改](https://github.com/dotnet/runtime/pull/116109) 一次排序会比较很多次，因此每次调用少做一点工作也值得。

### 空白搜索有了专门的 API

.NET 11 增加了 `ContainsAnyWhiteSpace`、`IndexOfAnyWhiteSpace` 等方法，调用方不必各自准备相同的空白字符搜索集合。[实现修改](https://github.com/dotnet/runtime/pull/111439)

验证一整段标识符里没有空白，需要把整段扫完，批量搜索很合适。去掉开头空白则不同：如果第一个字符就不是空白，逐字符循环看一次就结束，向量搜索的准备成本可能反而更显眼。因此，这类方法的收益也与输入中匹配的位置有关。

这里按文本空白规则处理。JSON 等协议只允许几种特定空白，解析协议时仍要使用对应的字符集合。

## 10. 集合与 LINQ：已经知道数量、顺序，就利用起来

### 构造冻结字典时，先准备好容量

`ToFrozenDictionary` 有时需要先把输入放进一个普通字典，处理重复键，再建立最终的冻结结构。

如果输入是列表或其他能提供数量的集合，就没必要让中间字典从小容量开始，装满了再扩容。.NET 11 利用这个数量预设容量，减少分配、复制和重新组织哈希表的工作。[实现修改](https://github.com/dotnet/runtime/pull/128300)

这改善的是构造过程。冻结字典仍适合构建后反复查询的用途；构造一次只查一次，就未必值得付出准备成本。

### 空 HashSet 合并另一个 HashSet，可以复制现成的表

`UnionWith` 通常枚举输入，逐项计算哈希、检查是否已经存在，再插入。但目标集合为空，输入又是使用相同有效比较器的 `HashSet` 时，这些元素已经按相同规则去过重了。

.NET 11 会利用已有的构造方法复制源集合的数据，不必从头逐项重建。[实现修改](https://github.com/dotnet/runtime/pull/122952)

比较器相同是必要条件。比如一个集合忽略大小写，另一个区分大小写，`"a"` 与 `"A"` 在两边就有不同的重复规则，不能直接套用源集合的结果。

`Dictionary.Remove` 则优化了自己的查找循环：将值类型键、默认比较器的常见情况单独处理。这个循环不用考虑另一路的比较器虚调用，JIT 就更容易把临时值留在寄存器里，少向栈上保存和取回。[实现修改](https://github.com/dotnet/runtime/pull/125884)

### FindAll 只找到一两项时，少建一个临时 List

`Array.FindAll` 不知道最终有多少匹配项，需要先收集，最后再返回结果数组。若一开始就建立 `List<T>`，哪怕只找到一个元素，也要为列表对象和内部数组付出分配成本。

.NET 11 先用小块固定大小的内联存储收集少量结果，装不下时再使用更大的存储。[实现修改](https://github.com/dotnet/runtime/pull/120336)

返回给调用方的非空结果数组仍然需要创建，省掉的是收集过程中的临时容器。临时空间也不宜无限增大，否则没有结果的调用都要承担较大的栈帧成本。

### SetEquals：对面已经是集合，就别再去重

比较 `{1, 2}` 和输入 `[1, 1, 2]`，集合意义上是相等的。因此，面对任意 `IEnumerable<T>`，`SetEquals` 需要考虑重复和顺序，不能直接比较枚举项数。

但两边都是采用兼容比较器的哈希集合时，就已经知道元素没有重复。先比较数量，再检查成员是否都存在即可，不必再建立一份临时集合去重。.NET 11 为 `ImmutableHashSet.SetEquals` 增加了这种处理。[实现修改](https://github.com/dotnet/runtime/pull/126309)

两边如果还是按相同规则排序的集合，比较会更简单：

```text
左侧：1 → 4 → 7 → 9
右侧：1 → 4 → 8 → 9
      相同 相同 不同，到这里就能结束
```

两个枚举器一起往前走，每个位置比较一次即可。`ImmutableSortedSet.SetEquals` 现在会利用这一点，避免再建临时树，也避免对每一项分别做一次树查找。[实现修改](https://github.com/dotnet/runtime/pull/126549)

### 连续 Append，不应该让每个元素都穿过一长串迭代器

```csharp
IAsyncEnumerable<int> sequence = AsyncEnumerable.Empty<int>();
for (int i = 0; i < count; i++)
{
    sequence = sequence.Append(i);
}
```

如果每次 `Append` 都在原来的序列外面再套一层迭代器，取最早的元素时，就得经过所有外层。后加入的元素经过的层数少一些，但总工作量会累积起来。

只追加四项，就可以看出问题：第一项经过四层，第二项三层，最后两项分别两层和一层，总计十次传递。按这个方式估算，追加一千项就是 `1000 × 1001 / 2 = 500500` 次，实际结果却只有一千项。

.NET 11 为异步 `Append`、`Prepend`、`Concat` 合并了连续操作的表示，直接记录需要追加的元素或连接的序列，枚举时依次访问。这样就不必每多写一个操作符，给此前的所有元素多加一层转交。[实现修改](https://github.com/dotnet/runtime/pull/122389)

这项改进在 LINQ 迭代器里，与前面 Runtime Async 改变异步方法执行方式是两件事。前者减少需要走的迭代层数，后者减少挂起、恢复和方法间传递结果的开销。

### Sum 少查几次溢出，Min/Max 少做一段收尾

整数 `Sum` 的向量循环需要检测溢出。它可以一边计算，一边记下是否有某个位置发生过溢出；但过去还会频繁取出这份标记，判断是否跳到抛异常的代码。

.NET 11 保留溢出记录，把向量部分的判断推迟到最后统一做，减少正常循环里反复确认“没有溢出”的分支。循环也改用安全的 span 切片组织。[实现修改](https://github.com/dotnet/runtime/pull/127429)

`Min` 和 `Max` 改进的是最后几步。前面即使已经向量化，最后也要从每个向量元素的候选值里找出总的最值。旧路径对一些小整数类型会把向量写到栈上，再逐项比较；新实现继续用向量重排和比较完成合并。[实现修改](https://github.com/dotnet/runtime/pull/127995)

该 PR 的 Neoverse-N2 基准里，16 项 `byte` 最大值从 51.54 ns 降到 1.85 ns，而同长度 `int` 是 1.72 ns 与 1.84 ns。改善主要来自小元素类型原先较慢的收尾方式，其他类型原本就没付出同样的成本。这是主干与 PR 版本的测量。

### FullJoin 同时保留两边没匹配上的记录

用订单和付款记录举例：

- 内连接只保留匹配上的订单与付款。
- 左连接还保留没有付款的订单。
- 完整外连接再加上没有找到订单的付款记录。

.NET 11 新增 `FullJoin`，可以直接完成第三种需求，省去调用方用多组查询拼接、再回头搜索另一侧未匹配记录的写法。[实现修改](https://github.com/dotnet/runtime/pull/127236)

例如订单键为 `{1, 2}`、付款键为 `{2, 3}`，结果里既有键 2 的匹配，也有单独的订单 1 和付款 3。如果某个键在左侧有两条、右侧有三条，匹配部分仍然会产生六个组合，这是连接本来要求的结果。

`Queryable` 也有对应 API，但数据库查询提供程序是否能将它翻译成 SQL，还要看提供程序自己的支持情况。

<a id="io"></a>

## 11. I/O：少占等待线程，少复制临时缓冲

### 异步读子进程输出，过去仍可能占着线程

父进程可以异步读取子进程重定向后的标准输出。但 Windows 上旧的管道读端是同步句柄，调用异步方法时，底层仍可能让线程池线程阻塞在原生读取里。

子进程迟迟不输出，这个线程就跟着等。并发启动很多子进程时，等待输出可能占去不少工作线程。

.NET 11 把父进程读取 stdout/stderr 的管道端改成支持 overlapped I/O，也就是 Windows 的异步 I/O 方式。读取尚未完成时，可以等系统通知完成，而不必让一个线程一直阻塞在那里。子进程写端继续保留原有的同步行为，标准输入不属于这次调整范围。[实现修改](https://github.com/dotnet/runtime/pull/125643)

### 同步读异步句柄，省去多余的完成回调

反过来的情况也存在。Windows 文件句柄打开时已经决定采用 overlapped I/O，后来即使调用同步的 `RandomAccess.Read`，底层仍要按这个句柄的方式发起读取。

调用线程要等结果，旧实现却同时还注册了 I/O 完成回调。读完以后，两边需要协调结果和资源释放，事情做了两份。

.NET 11 利用 `OVERLAPPED.hEvent` 的低位约定，让系统完成时只通知等待事件，不再往完成端口投递那次回调。调用线程醒来，取得结果并清理即可。[实现修改](https://github.com/dotnet/runtime/pull/126845)

这两项改动一个是减少阻塞等待的线程，一个是减少不需要的回调。虽然都涉及异步句柄，解决的问题正好不同。

### 已有输入和输出内存，可以直接压缩

假设待压缩数据已经在内存里，输出也准备写进租来的缓冲区。若为了调用压缩接口，再分别包装成流，就可能增加对象和内部缓冲。

.NET 11 提供了基于 span 的 Deflate、ZLib、GZip 编解码 API，支持一次处理和分块处理。[实现修改](https://github.com/dotnet/runtime/pull/123145)

```csharp
using System.IO.Compression;

static bool TryCompressPayload(
    ReadOnlySpan<byte> payload,
    Span<byte> output,
    out int written)
{
    return DeflateEncoder.TryCompress(payload, output, out written);
}
```

输入直接取自 `payload`，输出直接写进 `output`。成功时，`output[..written]` 就是压缩结果；失败时，不能把缓冲里已有的部分内容当作完整结果发出去。这段调用省去了调用方的流包装，底层压缩器仍然需要管理自己的状态。[API 实现](https://github.com/dotnet/runtime/blob/main/src/libraries/System.IO.Compression/src/System/IO/Compression/DeflateEncoder.cs)

分块处理时，调用方还需要看清哪些输入已被使用、写出了多少字节，以及是否已经完成。如果输出先满，就提交这部分数据，换一块输出空间，再从尚未使用的输入继续。原来流帮忙处理的事情，现在可以与自己的缓冲池或发送队列配合处理。

### tar 预先算好大小，ZIP 复用读取缓冲

GNU tar 处理长文件名时，需要把名字编码为 UTF-8，再加一个终止字节。旧实现先编码成新数组，又写进逐步增长的 `MemoryStream`，名称在两个缓冲之间复制，流还可能扩容。

现在先算出最终需要多少字节，分配一个数组，直接把编码结果写进去，再让 `MemoryStream` 使用这个数组。少了中间数组，也少了流扩容时的复制。[实现修改](https://github.com/dotnet/runtime/pull/123835)

ZIP 中央目录读取则从数组池租用工作缓冲，用完归还；部分原来为拼接、切片创建的数组，也改用 span 或 memory 表示。[实现修改](https://github.com/dotnet/runtime/pull/123836) 这些缓冲由读取过程管理，不能在归还后继续让外部代码使用它们。

<a id="networking"></a>

## 12. 网络：从连接建立到 HTTP 请求，分别省掉哪些工作

### IPv6 连不上，不必一直等它失败才试 IPv4

同一个主机名可能同时有 IPv6 和 IPv4 地址。如果按顺序尝试，排在前面的 IPv6 路径一直丢包，就会卡在超时上；哪怕 IPv4 完全可用，也得等前一次失败才轮到它。

.NET 11 为使用 `SocketAsyncEventArgs` 的连接 API 增加了可选并行策略。`ConnectAlgorithm.Default` 保留默认方式，`ConnectAlgorithm.Parallel` 请求并行连接。在支持双栈、域名端点未指定地址族等条件下，IPv4 和 IPv6 分别解析、推进连接，每类地址内部仍依次尝试，先成功的连接交给调用方。[实现修改](https://github.com/dotnet/runtime/pull/106374)

这样，健康的 IPv4 路径就能先完成，不再被坏掉的 IPv6 路径拖到超时。另一条路线稍后也成功时，多出来的连接需要清理；两边都失败，才算整个操作失败。

这是调用方选择的策略，可能短暂多占一些连接资源。它改善的是特定网络故障下的建连等待，不能从这个新重载推断所有 `HttpClient` 连接都已改用同样算法。

### Unix 上，异步连接完成后可以恢复阻塞模式

Unix 的异步 socket 通常先设成非阻塞模式，读取暂时没有数据时，通过 `epoll`、`kqueue` 等机制等待通知。

有些程序只在连接时用 `ConnectAsync`，连接后却一直同步 `Send`、`Receive`。旧实现一旦把 socket 设成非阻塞，就不再切回去，于是后续同步调用也需要额外的等待机制来模拟阻塞。

.NET 11 在连接成功、用户没有明确设置 `Blocking = false` 时恢复阻塞模式，后续同步读写就可以直接使用原生阻塞调用。如果以后又发起异步读写，再按需要切到非阻塞模式。[实现修改](https://github.com/dotnet/runtime/pull/124200)

切换放在连接完成之前，利用的是这个时机的使用约束，而不是在并发读写期间随意来回切换模式。

### Windows 的扩展函数缓存，命中时不再排队加锁

Windows 的 `AcceptEx`、`ConnectEx` 等函数入口由 Winsock 提供程序提供，.NET 会动态查找并缓存它们。每个 socket 初次使用相关异步功能时，都可能查询这份缓存。

缓存通常只有少量条目，填好以后几乎都是读取。旧实现仍让每次查询进入同一把锁，大量 socket 同时开始工作时，连已经命中的读取也要排队。

新实现先读数组快照，命中就返回；没找到才加锁，再检查一次，必要时建立包含新条目的数组并发布。已有读者可以继续使用旧数组。[实现修改](https://github.com/dotnet/runtime/pull/124997)

因为新增条目少，复制数组的成本容易被大量无锁读取摊薄。这里利用的是这份缓存的实际读写比例。

### Linux 的 SslStream，少让密文和明文中转几次

OpenSSL 通过 BIO 与调用方交换数据。旧的 `SslStream` 使用内存 BIO：收到密文后先复制进去，解密结果又经过 `SslStream` 内部缓冲，最后再复制到用户提供的内存。

.NET 11 改用自定义 BIO，让 OpenSSL 在调用期间直接访问 .NET 已有的缓冲，并尽可能把解密后的明文直接写进用户目标缓冲。加密输出也能直接写进待发送的缓冲。设置缓冲、执行 OpenSSL 操作和清理的几个原生调用，还合并成了一个。[实现修改](https://github.com/dotnet/runtime/pull/128245)

```text
旧的常见解密过程：
收到密文 → 复制到内存 BIO → OpenSSL 解密
         → SslStream 内部明文缓冲 → 复制到用户缓冲

新的常见解密过程：
收到密文 → 自定义 BIO 直接读取现有缓冲 → OpenSSL 解密
         → 尽可能直接写入用户缓冲
```

这里省掉的是 .NET 与 OpenSSL 之间的一些中转复制。OpenSSL 内部仍有处理，目标缓冲太小或者出现 TLS 控制消息时，也仍要保存剩余数据。托管内存的地址只在有效的原生调用期间交给 BIO 使用，调用结束后不能继续保留它。

证书协商也少了几项临时分配：Windows 和 macOS 解析颁发者名称时，直接用 span 引用原有编码，不再先复制成数组；macOS 整理较小证书链的原生句柄时，使用栈上临时空间。[名称处理](https://github.com/dotnet/runtime/pull/123904)、[句柄处理](https://github.com/dotnet/runtime/pull/123905)

### HTTP 头、multipart 和 URI 中的重复分配

自动解压启用后，handler 已经知道支持哪些压缩算法。多数请求又不会手工设置 `Accept-Encoding`，因此可以复用预先准备好的组合值，不必每次建立集合、逐项添加和枚举。

响应没有 `Content-Encoding` 时，也可以直接查询是否存在，省去集合包装；需要解压时，尽量接管原内容头，而不是把每个头再复制到新集合。.NET 11 对这些常见情况做了专门处理。[实现修改](https://github.com/dotnet/runtime/pull/122676)

`MultipartContent` 的 boundary 在创建对象时已经确定。新实现把起始和结束分隔内容提前编码成字节，序列化时直接复用，减少反复拼接和编码。[实现修改](https://github.com/dotnet/runtime/pull/124963)

另外，HTTP/3 的 trailers 直接写入最终响应头集合，省掉临时列表；检查哪些连接应被回收时，直接查看现有列表的数据，减少先复制成数组的分配。[trailers](https://github.com/dotnet/runtime/pull/122677)、[连接检查](https://github.com/dotnet/runtime/pull/131142)

URI 解析也分两处提速：寻找 `: / ? #` 等分隔符时更多使用批量搜索；处理非 ASCII 的路径、查询和片段时，集中构造最终字符串，避免每处理一部分都拼接出新的中间字符串。[分隔符搜索](https://github.com/dotnet/runtime/pull/124433)、[字符串构造](https://github.com/dotnet/runtime/pull/122038)

这些操作大多发生在每个请求或每个连接上，单次节省不多，请求量高时却会持续消耗 CPU 和分配内存。它们与远端响应需要等待多久，是网络性能里需要分别观察的两部分。

<a id="json"></a>

## 13. JSON：更快地跳过空白，找到需要转义的字符

### 连续几个空格，可以一次找到结尾

读取带缩进的 JSON 时，属性前面可能有一长串空格。旧的 `Utf8JsonReader` 会逐字节判断是不是空白；.NET 11 使用 `SearchValues` 和 `IndexOfAnyExcept`，直接查找第一个不是空白的字节，跳过前面整段。[实现修改](https://github.com/dotnet/runtime/pull/129701)

这里只认 JSON 允许的四种空白：空格、制表符、回车、换行。把这四个字节组成一个可复用的搜索集合，底层就能按硬件条件批量比较。

下面的代码只演示如何找到空白前缀的长度：

```csharp
using System.Buffers;

static class JsonWhiteSpaceDemo
{
    private static readonly SearchValues<byte> WhiteSpace =
        SearchValues.Create(" \t\r\n"u8);

    public static int GetPrefixLength(ReadOnlySpan<byte> input)
    {
        int index = input.IndexOfAnyExcept(WhiteSpace);
        return index < 0 ? input.Length : index;
    }
}
```

输入开头就是 `{`，返回零；四个空格后才是 `{`，返回四；整个片段都是空白，就返回片段长度。搜索集合在初始化时准备一次，后面的调用重复使用。

真正的 JSON 读取器还要记录行号和行内位置。如果跳过的空白里有换行，就需要更新这些信息，出错时才能继续报告正确的位置。输入分成多个内存片段时，也要在当前有效片段内搜索，再处理下一片段。

这项改进对缩进很多的 JSON 更有用。PR 的本地扫描驱动测量中，压缩 JSON 是 45.4 μs 与 45.5 μs，基本不变；中等缩进样例从 849 μs 变成 574 μs；深层缩进样例从 1248 μs 变成 519 μs。这些是该实验的 A/B 结果，反映的是空白扫描的影响，并非所有 JSON 序列化都会按同样比例变快。

### 普通文字整段复制，遇到特殊字符再转义

假设要输出的字符串是一长段普通字母，最后才出现一个换行符。写入器可以先找到换行的位置，把前面的普通文字一起复制，再写出换行的转义形式。

默认编码规则是固定的，哪些字符要转义可以提前准备好。.NET 11 在默认规则下使用预计算的 `SearchValues` 集合，减少查找时经过编码器的间接调用。[实现修改](https://github.com/dotnet/runtime/pull/129781) 自定义编码器仍需按自己的规则处理。

### 转义后的空间够了，就不必每写一个字节再检查

一个控制字符可能展开为 `\u0001`，占六个 ASCII 字节。写入器会先确保输出缓冲有足够空间，然后把这些字节逐个写进去。

如果辅助方法看不到“这段空间足够六字节”的关系，JIT 可能还会为每次写入分别检查边界。.NET 11 调整了传给辅助方法的可写范围，让这个长度更明确，连续写入时便能少做重复检查。[实现修改](https://github.com/dotnet/runtime/pull/129803)

这与前面的边界检查例子是同一回事：调用方已经保证了空间，JIT 能把这个保证继续用到实际写入处。前一项改进加快寻找特殊字符，这一项则让找到之后的转义写入更便宜。

<a id="benchmarking"></a>

### 14.1 Benchmarking Setup：先看两行结果在比较什么

原文主要用 BenchmarkDotNet 测量。读表时先确认比较对象：同一代码分别跑在 .NET 10 和 .NET 11 上，可以看版本升级的影响；同一个运行时上比较两种写法，则是在看代码差异；PR 里的 `main` 与修改版，又是该 PR 开发时的两套构建。

Runtime Async 就适合在同一运行时里比较两种编译方式，这样能尽量排除其他版本变化。若同时换了 SDK、运行时、输入和机器，就难以判断究竟是哪一项让程序变快。

表中的几列也要分别理解：

| 列 | 说明什么 |
| --- | --- |
| Mean | 一次被测操作的平均耗时 |
| Ratio | 相对基线的比例，先确认谁被设为基线 |
| Allocated | 被测操作的分配量，不等于整个应用的内存占用 |
| Code Size | 生成的机器代码大小，不等于执行耗时 |

例如循环克隆会多生成一份循环，代码变大，却可能执行得更快。分配量下降也不表示 GC 暂停按同样比例缩短，因为还要看对象存活多久、何时回收。

自己复现时使用 Release 构建，保持机器和输入一致，并明确测冷启动还是预热后的执行。需要排除的一次性初始化放在准备阶段；如果研究的恰好是首次调用成本，就要把初始化算进去。

<a id="assertions"></a>

### 14.2 Assertion Propagation：前面已经知道的，后面接着用

一次整数除法成功执行，除数就不可能是零；数组创建成功，请求长度就不是负数；写入 `array[5]` 成功，数组就至少有六项。

JIT 可以把这些结论记下来，处理后面的代码时继续使用。比如刚写完 `array[5]`，再读 `array[4]`，不需要又检查一次长度。.NET 11 增加了从这些操作中收集信息的能力。[实现修改](https://github.com/dotnet/runtime/pull/124711)

这类信息还可能在分支汇合时丢掉。`cache ??= new Cache()` 有两种情况：原来已经有对象，或者新建一个对象。无论哪种情况，表达式结果都非空。.NET 11 改善了对合并结果的分析，后续访问不必再查一次空引用。[实现修改](https://github.com/dotnet/runtime/pull/127810)

“断言传播”就是让这些已经成立的条件继续影响后续优化，不要求开发者额外写 `Debug.Assert`。前面的边界检查消除，就经常需要它提供信息。

<a id="simplification"></a>

### 14.3 Simplification：几个判断，可以换成一个更简单的判断

检查 `x` 是不是 6、7、8，可以逐个比较，也可以检查它是否落在这个连续区间。用非 checked 的整数运算表达，等价写法是：

```csharp
unchecked((uint)(x - 6)) <= 2
```

6、7、8 减去 6 后分别是 0、1、2，能通过比较；5 减去 6 后转成很大的无符号数，也会被排除。.NET 11 改善了对连续取值判断的识别，包括不从零开始的范围。[零起点范围](https://github.com/dotnet/runtime/pull/124567)、[非零起点范围](https://github.com/dotnet/runtime/pull/128524)

另一个例子是两个属性分别返回固定字符串。C# 编译器通常不能把属性调用当作常量，但 JIT 内联后看到了具体字符串，就可能在编译时把比较做完，让方法直接返回 `true` 或 `false`。[SequenceEqual 常量计算](https://github.com/dotnet/runtime/pull/121985)

还有一些更小的替换：`byte x` 的 `255 - x` 等价于 `x ^ 255`，后者可能少一条指令。[实现修改](https://github.com/dotnet/runtime/pull/126529)

小型条件分支也可以换成条件选择指令，但是否划算要看两边做多少工作。若原来的分支经常跳过一大段计算，改成两边都计算再选结果反而不合算，JIT 需要在这些情况之间做选择。

<a id="intrinsics"></a>

### 14.4 Intrinsics：JIT 认识这个 API，就可以直接生成对应操作

普通方法调用需要进入方法执行；intrinsic 则是 JIT 特别认识的操作。它知道某个 API 在数前导零、比较向量或者重排元素，可以直接生成合适的机器指令。

例如泛型代码中的枚举 `a.Equals(b)`，可能调用 `Enum.Equals(object)`，把值装箱后才比较。.NET 11 在已知枚举类型时，直接比较底层整数，装箱也就不再需要。[实现修改](https://github.com/dotnet/runtime/pull/122779)

泛型数学的 `Log2` 也修复了一处识别问题：过去分析时丢掉了精确的有符号、无符号类型信息，本来可以走的 intrinsic 没有被用上。现在按正确类型处理，就能采用相应的位扫描等实现。[实现修改](https://github.com/dotnet/runtime/pull/128678)

向量 API 新增了构造和组合元素的方式，例如把 `[a, b]` 与 `[x, y]` 交错成 `[a, x, b, y]`。调用方描述想怎样排数据，由 JIT 选择平台指令，不必为同一种排列分别编写各平台代码。[相关 API](https://github.com/dotnet/runtime/pull/129627) 宽向量的[求和收尾](https://github.com/dotnet/runtime/pull/127329)和 [256/512 位常量处理](https://github.com/dotnet/runtime/pull/127402)也继续改进。

有趣的是，专用指令不一定最快。一个点积实现改成乘法、重排和加法的组合后，在目标硬件上比原来的专用点积指令表现更好。[实现修改](https://github.com/dotnet/runtime/pull/125666) 因此，指令少不一定耗时少，还要看 CPU 怎样执行它们。

.NET 11 也继续补充 [APX 条件指令](https://github.com/dotnet/runtime/pull/127536)和 [Arm64 可伸缩向量支持](https://github.com/dotnet/runtime/pull/129852)。这些要配合相应硬件、操作系统和运行时设置，不能从 API 支持情况直接推断任意机器都会执行那些指令。

<a id="registers"></a>

### 14.5 Register Allocation：参数已经在寄存器里，就直接取字段

小结构体有时会把多个字段一起放进一个参数寄存器。例如低位保存标志，高位保存整数。旧实现可能先把整个寄存器写到栈上，再按字段位置把两个值分别读回来。

.NET 11 支持直接从参数寄存器中提取这些字段，少了一次写栈和后续读取。[实现修改](https://github.com/dotnet/runtime/pull/112740)

这属于寄存器分配和代码生成工作：CPU 的寄存器数量有限，JIT 要决定哪些值一直放在里面，哪些暂时写到栈上。对只是读取一个字段的小方法，那些存取动作本来就占了很大一部分工作。参数具体怎样传递取决于平台，所以改进在不同架构上的表现也会不同。

<a id="jit-throughput"></a>

### 14.6 JIT Throughput and Cleanup：JIT 自己也不能花太多时间

JIT 在应用运行期间工作。如果为了让某个很少执行的方法省一条指令，先做大量分析，编译成本可能比收益还高。

.NET 11 删除了一些全局断言传播中耗时较多、实际效果较小的维护逻辑，把编译时间留给更有用的分析。[实现修改](https://github.com/dotnet/runtime/pull/123856)

完成优化后，还要收拾剩下的代码。比如几个分支最后都返回相同值，可以共用结尾；内联后发现某个调用一定抛异常，后面的代码也就走不到了。重复返回或抛出部分的合并得到改进，代码更短，也可能让前面的判断进一步简化。[实现修改](https://github.com/dotnet/runtime/pull/128515)

OSR 则处理运行到一半的热点循环：程序不必先退出方法，就能切换到优化版本。但从循环中间进入，和从方法开头进入不同，收集的路径信息有时对不上。新的处理会在部分不匹配情况下估计后续路径概率，而不是直接触发断言。[实现修改](https://github.com/dotnet/runtime/pull/127363)

<a id="startup"></a>

### 14.7 Startup and Deployment：程序还没进入 Main，也能少做一些工作

启动时，宿主要读依赖信息、查找文件、准备程序集列表，运行时再加载和初始化类型。减少这里的重复处理，就能让应用早一点开始执行业务。

例如 servicing 目录存在时，旧的依赖解析会多做一些文件存在性查询。.NET 11 把检查限制在确实需要探查该目录的地方，减少启动阶段的 I/O。[实现修改](https://github.com/dotnet/runtime/pull/123568)

ReadyToRun 会提前准备一部分机器代码。不过，泛型默认比较器若通过反射式方法创建，提前编译时可能没看出以后需要哪个具体比较器。新实现换用能专门化的创建方法，让 R2R 把相关类型和代码一起准备好。[实现修改](https://github.com/dotnet/runtime/pull/126204)

框架内部的 EventSource 也把一些元数据准备移到构建阶段，用源生成器提前生成，减少第一次使用时的发现和初始化工作。[实现修改](https://github.com/dotnet/runtime/pull/121180)

NativeAOT 的一个小型元数据分配器，则改用更适合小块内存的分配方式，避免 Windows 上为少量数据按较大的虚拟地址区域预留空间。[实现修改](https://github.com/dotnet/runtime/pull/122822)

移动端采用 CoreCLR 的工作也让这些改进能在更多平台共享。编译方式仍受平台限制：例如 iOS 设备上的动态代码限制没有消失，可以结合预编译和解释器执行。具体平台的默认选择，要对照使用的 SDK 版本。[MAUI 运行时与编译方式](https://learn.microsoft.com/en-us/dotnet/maui/deployment/runtimes-compilation)

<a id="globalization"></a>

### 14.8 Globalization：时区规则算过一次，就尽量复用

一个时区的偏移可能随夏令时和年份变化。规则若写成“某月第几个星期日切换”，还需要算出那一年实际的日期。每次转换时间都重新解释这些规则，会重复不少工作。

.NET 11 按年缓存已经解析好的切换信息，同一年后续转换可以复用。`DateTime.Now` 也可以复用当前有效的 UTC 偏移，直到需要重新判断的切换时刻。[TimeZoneInfo 修改](https://github.com/dotnet/runtime/pull/119662)

ASCII 大小写转换则尽量先由托管代码处理，推迟或避免为了简单字符串加载 ICU。遇到需要完整全球化处理的输入，再进入相应实现。[实现修改](https://github.com/dotnet/runtime/pull/120685)

日期格式还有两处直接的改进。`O` 格式的小数秒固定七位，恰好与每秒一千万个 tick 对应。例如 `1234567` 就是 1,234,567 个 tick，可以直接使用，不必先转浮点再计算回来。[解析修改](https://github.com/dotnet/runtime/pull/129005)

`DateTime.ToString("G", CultureInfo.InvariantCulture)` 的格式也已确定，新实现直接走固定格式处理，省去一般格式解析。这个条件不包括自定义文化信息，也不包括带偏移的 `DateTimeOffset`。[格式化修改](https://github.com/dotnet/runtime/pull/129374)

<a id="strings"></a>

### 14.9 Strings and Spans：编码时少查位置，拼接时少建临时对象

UTF-8 处理里的纯 ASCII 部分可以快速批量复制。旧 Arm64 循环即使一整块全是 ASCII，也可能先计算第一个非 ASCII 字节的位置。现在先判断有没有，确实发现了，再计算具体位置，纯 ASCII 输入就少做一段工作。[实现修改](https://github.com/dotnet/runtime/pull/121382)

UTF-16 转换还需要检查代理项配对并统计输出长度。相关修改整理了向量化验证的实现，让 x86 和 Arm64 共用更多算法代码，把指令差异放到少量辅助方法里。[实现修改](https://github.com/dotnet/runtime/pull/121981)

Base64 编码有时需要插入换行。旧实现为这种选项使用单独的标量处理，现在复用已有的高效编码逻辑，只在行边界处理换行。[实现修改](https://github.com/dotnet/runtime/pull/123403)

原地 Base64 解码也用上了向量实现。四个输入字节产生三个输出字节，读指针比写指针走得快；只要把每次向量写入的完整范围和尾部也验证好，就不会覆盖尚未读取的数据，便能复用已有的批量解码逻辑。[实现修改](https://github.com/dotnet/runtime/pull/131333)

`string.Concat` 接受 `IEnumerable<string?>` 时，现在会识别实际输入是不是数组或列表。如果是，就直接利用连续存储的 span 拼接，少走通用枚举过程。[实现修改](https://github.com/dotnet/runtime/pull/130361) 代码页查询缓存则改用 `ConcurrentDictionary`，让已命中的读取少加一次锁。[实现修改](https://github.com/dotnet/runtime/pull/125001)

<a id="diagnostics"></a>

### 14.10 Diagnostics：日志、指标和追踪少添一些额外开销

分布式追踪会反复验证 trace ID、处理随请求传递的 baggage 文本。.NET 11 用批量搜索改进字符验证；内容不需要转义时，尽量一次追加整段，减少逐字符判断和追加。[实现修改](https://github.com/dotnet/runtime/pull/119673)

指标回调也省掉了一项很小却频繁的分配。某些回调只返回一个值，旧实现仍先把它放进单元素数组，再按通用序列处理。现在对内建单值回调直接发送测量，不再建立这份数组。[实现修改](https://github.com/dotnet/runtime/pull/128039) PR 的本地实验中，`Func<T>` 路径从每次 72 B 变为 0 B；用户自己创建数组返回多个值的情况，仍保留那份结果数组。

`MemoryCache` 的计数器则调整了内存布局。两个线程虽然更新不同字段，但字段落在同一缓存行时，仍会来回争夺这条缓存行的写入权限，这叫伪共享。新布局把不相关的热点计数器隔开，用一些额外空间减少竞争。[实现修改](https://github.com/dotnet/runtime/pull/131470)

EventSource 日志的 JSON 路径，改为复用线程本地的 `MemoryStream` 和 `Utf8JsonWriter`，避免每条日志都创建一套对象。最后返回的 JSON 字符串仍要分配，缓存的工作缓冲也需要控制大小。[实现修改](https://github.com/dotnet/runtime/pull/131229)

进程相关 API 还有几项改进：

- Unix 启动参数和环境变量直接写进集中分配的原生内存，减少临时 `key=value` 字符串和逐项分配。[实现修改](https://github.com/dotnet/runtime/pull/126201)
- macOS 常见启动方式使用 `posix_spawn`，减少先 `fork` 再 `exec` 的部分准备工作；需要切换用户等情况仍有相应回退。[实现修改](https://github.com/dotnet/runtime/pull/126063)
- 只查询 `ProcessName` 时，不再先读取完整的进程信息。[实现修改](https://github.com/dotnet/runtime/pull/126449)
- 仅使用本地进程 API 的 AOT 应用，更容易裁剪掉远程进程查询及其依赖。[实现修改](https://github.com/dotnet/runtime/pull/126338)

这些功能往往跟着每个请求或每轮采集执行。即使业务计算没变，日志和监控少占一些 CPU、少创建一些对象，应用的总成本也会下降。

<a id="cryptography"></a>

### 14.11 Cryptography：加解密之外，还有解析和资源准备

证书和密钥使用的 ASN.1 格式有很多嵌套结构。如果每进入一个子结构就创建一个 reader 对象，解析过程会产生不少临时分配。

新的 `ValueAsnReader` 是基于 span 的 `ref struct`，可以在原有字节上记录读取位置、取得子结构，而不必每层都新建堆对象。.NET 11 也把它用于更多现有解析代码。[API 实现](https://github.com/dotnet/runtime/pull/125254)、[使用范围扩展](https://github.com/dotnet/runtime/pull/125346)

ASN.1 中一些字符串只允许特定字符，例如 IA5String 要求 ASCII。验证和转码现在能批量处理；发现非法字符以后，再定位到具体位置，保持原来的错误报告。[实现修改](https://github.com/dotnet/runtime/pull/131109)

AES 密钥包装需要多次执行块加密。旧实现每处理一块都可能创建、销毁原生 cipher，重复初始化花了不少时间。Windows 和 Apple 的改进会在一次包装或解包操作内复用 cipher，让初始化不再跟着每个块重复。[Windows 修改](https://github.com/dotnet/runtime/pull/129921)、[Apple 修改](https://github.com/dotnet/runtime/pull/129911)

证书链验证还有缓存方面的改进。Linux 的 CRL 即使已存在磁盘，每次使用仍可能重新打开、读取、解析。新的内存缓存可以复用已经解析好的对象，并按容量和使用情况淘汰。[实现修改](https://github.com/dotnet/runtime/pull/123562)

AIA 则允许从证书指定的位置下载缺少的颁发者证书。多个线程同时验证相似证书链时，新实现让它们共享相同下载，减少向同一个地址重复请求。[实现修改](https://github.com/dotnet/runtime/pull/130456) 对这种负载，省下来的文件和网络工作，可能比加密指令本身的微调更明显。

<a id="next"></a>

### 14.12 What’s Next：继续优化，也继续用真实负载检验

文章结尾把重点放在后续迭代和反馈。Runtime Async 还有可优化的情况，硬件支持也会继续扩展；但每次给 JIT 增加分析，都要考虑编译本身的时间和生成代码的大小。

对使用者而言，可以先找自己的程序是否经常执行文章中的那些操作：反复拼接异步 LINQ、扫描带缩进的 JSON、更新大量引用字段，或者建立大量连接。找到了对应负载，再测升级前后的差异，比拿最大的基准倍数估算整个应用更可靠。

## 在自己的程序里怎样验证

先选一条实际最忙的业务路径，固定机器、输入和并发量，比较耗时、CPU、分配率和 GC 暂停。冷启动与预热后分开测，异常路径也单独测。

基准中的提升还要结合它在业务里所占的比例。假设请求原本消耗 100 个单位 CPU，其中 20 个花在某个热点；即使这个热点成本减半，其他部分不变，总成本也只是从 100 降到 90。

同样，[Matrix4x4 的 PR](https://github.com/dotnet/runtime/pull/123954) 报告行列式基准从 3.487 ns 降到 2.971 ns，约减少 15% 时间，说的是该环境下这一操作的变化，不是整个数值库或应用的提升。

最后还要看怎么才能用上改进。JIT 和基础库内部优化常常随运行时升级生效；Runtime Async 需要相应编译方式；UTF-8 数值解析和新的压缩 API 则需要改用对应入口。测试时把这些动作分开，结果才容易解释。
