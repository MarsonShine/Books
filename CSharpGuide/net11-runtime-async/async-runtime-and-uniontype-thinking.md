# .NET 11 Runtime Async 与 Union Type：从问题出发的思考过程

这份文件不是成文版博客，而是把推导过程摊开：**旧方案在解决什么问题、旧方案为什么会长成那样、它的代价是什么、新方案把哪部分职责搬走了、因此换来了什么能力，又引入了什么边界**。

---

## 一、先建立一个统一视角：这两个功能其实在解决同一类问题

表面上看，`runtime async` 属于运行时，`union type` 属于语言；一个偏执行模型，一个偏类型系统，好像关系不大。

但如果往上一层抽象，它们都在做同一件事：

1. 过去某种能力并不是 CLR/C# 的一等公民，只能靠**编译器改写**或**库层约定**间接模拟。
2. 模拟方案可用，但会泄漏底层实现细节。
3. 现在运行时或语言开始**原生理解这类抽象**，于是调试、分析、优化、静态检查都更可靠。

可以用一句话概括：

- `runtime async`：把“异步控制流”从**编译器技巧**提升为**运行时语义**。
- `union type`：把“值只能属于若干类型之一”从**库与约定**提升为**语言语义**。

这就是理解这两个特性的总钥匙。

## 二、Runtime Async：为什么 `async/await` 以前必须是状态机？

### 2.1 先问根问题：同步函数为什么天然简单？

同步函数调用时，运行时已经有现成机制：

1. 调用方压栈。
2. 被调用方运行。
3. 局部变量活在栈帧里。
4. 返回时整个栈帧弹掉。

同步函数的控制流没有中断语义。它要么继续跑，要么抛异常，要么返回。

### 2.2 异步函数为什么困难？

`await` 的本质不是“稍后再继续”，而是：

> 一个函数执行到一半，必须把“未来从哪里继续、继续时需要哪些局部状态、结果回来后怎么接上后半段逻辑”保存起来，然后立刻把控制权交回去。

这和普通调用栈天然冲突，因为：

- 当前栈帧本来应该跟着返回一起销毁；
- 但 `await` 之后还要继续用到这个栈帧里的局部变量、异常上下文、分支位置。

所以语言实现者必须回答三个问题：

1. **挂起点在哪里？**
2. **恢复点在哪里？**
3. **恢复时要带回哪些状态？**

### 2.3 旧方案为什么是“编译器生成状态机”？

在没有运行时原生支持的前提下，最直接的办法是让编译器把：

```csharp
async Task<int> FooAsync()
{
    var x = 1;
    await BarAsync();
    return x + 1;
}
```

改写成“状态机对象 + 一个 `MoveNext()` 方法”的形式。

这个改写的思路是：

1. 用一个整数状态字段表示执行到了哪一步。
2. 把跨 `await` 仍要存活的局部变量提升成字段。
3. `await` 前保存状态，注册 continuation。
4. continuation 触发时再次进入 `MoveNext()`，根据状态字段跳到正确位置继续。

于是，**异步函数被手工编译成了协程对象**。

### 2.4 为什么这个设计会导致“栈很脏”？

因为你写的是：

```csharp
await OuterAsync();
```

但运行时实际看到的更像是：

1. 创建/初始化状态机
2. 调 `AsyncMethodBuilderCore.Start`
3. 进入 `MoveNext`
4. 命中 `await`
5. 挂 continuation
6. 未来 continuation 再次调 `MoveNext`

所以在**实时调用栈**里，调试器和 profiler 看到的大量帧根本不是你的业务方法，而是编译器和 builder 基础设施。

这不是“显示不够智能”，而是**底层执行结构本来就长这样**。

### 2.5 为什么异常栈看起来没那么糟？

这点特别容易误解。

异常传播是一个更特殊的观察点。传统 async 里，编译器早就对异常路径做了额外处理，例如借助 `ExceptionDispatchInfo` 尽量恢复更合理的异常栈信息。

因此：

- **实时栈**：会暴露大量状态机基础设施；
- **异常栈**：很多时候已经被清洗过，看起来没那么差。

所以 runtime async 主要改善的是**执行中的可观察性**，而不是“所有异常栈 suddenly 完全换一种样子”。

## 三、Runtime Async：运行时接管后，职责到底迁移了什么？

### 3.1 关键不是“没有状态”，而是“状态不再主要由编译器物化为用户可见结构”

很多人第一次听到 runtime async，会误以为：

> 哦，那就是没有状态机了。

这句话不够准确。

**异步挂起/恢复不可能没有状态。**  
只要一个方法能在 `await` 处暂停，然后稍后继续，它就一定需要某种形式的：

- 当前执行点
- 活跃局部变量
- continuation 信息
- 返回值/异常传播协议

真正变化的是：

> 这些状态不再主要通过 C# 编译器生成一个显式状态机类型来表达，而改由运行时直接理解和管理。

所以“没有编译器状态机”不等于“没有状态”，而是“状态的拥有者从编译器改写结果转向运行时机制”。

### 3.2 运行时原生 async 可以多做什么？

一旦 CLR/JIT 知道“这是一个 async 方法”，它就不再只看到普通 IL + 一堆库调用，而是知道：

- 这里是异步方法边界；
- 这里是挂起点；
- 这里是恢复点；
- 这里的某些局部需要跨挂起保活；
- 这里的 continuation 可以按运行时策略安排。

这会带来几个直接结果：

1. **调用链更接近源码结构**  
   因为运行时知道哪些帧是逻辑 async 帧，实时栈可以展示真实方法链。

2. **调试器更容易 step over `await`**
   因为它不需要再“跳进编译器生成的 MoveNext 基础设施”才能表达挂起与恢复。

3. **运行时可以做统一优化**
   比如更积极重用 continuation 对象、减少不必要的状态保存。

4. **为 AOT / R2R / JIT 统一实现铺路**
   这不是单纯语法糖，而是执行模型升级，所以预编译场景也能跟上。

### 3.3 Roslyn 现在大致做什么？

公开设计文档显示，编译器并没有把 async 完全“什么都不做”。它仍然需要：

- 把 async 方法标记成特殊的 `MethodImplOptions.Async` 方法；
- 在 `await` 场景下发出对 `AsyncHelpers.Await(...)` 等 helper 的调用；
- 对 `catch` / `finally` 中的 `await` 做必要重写，把异常先暂存，再在异常处理块外 await。

这说明一个很重要的事实：

> runtime async 不是“编译器完全退出舞台”，而是“编译器和运行时重新分工”。

编译器负责：

- 语义绑定基本不变；
- 生成符合 runtime async 协议的 IL；
- 处理某些必须在语言层做的结构性重写。

运行时负责：

- 把这些 IL 当成 async 方法来执行；
- 管理挂起/恢复；
- 暴露更干净的执行栈与更高效的内部实现。

### 3.4 为什么 helper API 是必要的？

因为编译器最终还是要落到 IL，而 IL 需要一个明确协议告诉运行时：

- “这里是 await 一个 `Task`”
- “这里是 await 一个 `Task<T>`”
- “这里是 await 一个任意 awaiter”

所以会有类似：

- `AsyncHelpers.Await(Task)`
- `AsyncHelpers.Await<T>(Task<T>)`
- `AwaitAwaiter<TAwaiter>(...)`

这些 helper 的意义不是“帮你完成 await 的业务逻辑”，而是**把 await 语义编码成运行时可识别的挂起点协议**。

### 3.5 为什么仍然存在限制？

因为 runtime async 不是魔法，它仍要面对“哪些状态能跨挂起安全保存”这个问题。

所以官方设计里会限制：

- 某些 `byref` / `ref-like` 场景不能跨 suspension 保活；
- `localloc`、`tail` 等低层 IL 机制有限制；
- 只支持 `Task` / `ValueTask` 及其泛型版本；
- 异常处理区域中的挂起点仍需要特定重写策略。

这背后的本质规律很简单：

> 能不能做 runtime async，不取决于语法写不写得出来，而取决于运行时是否能安全保存并恢复该执行状态。

## 四、Runtime Async：应该怎样建立正确心智模型？

### 4.1 不要把它理解成“新语法”

用户代码写法几乎不变。你还是写：

```csharp
await DoWorkAsync();
```

变化在于**这句代码被编译和执行的方式**。

### 4.2 也不要把它理解成“完全栈式协程”

它确实比“纯编译器状态机”更接近运行时原生协程，但它不是“无限制保存整条原生调用栈”的那种能力。

更准确的说法是：

> CLR 开始把 async 看成自己理解的一种方法执行模式，而不是完全依赖上层语言手工把它编码成状态机对象。

### 4.3 真正的收益排序

如果按开发者能感知到的优先级排序：

1. **实时栈更干净**
2. **调试体验更自然**
3. **分析工具更容易看懂逻辑调用链**
4. **某些 async 密集场景分配压力更低**
5. **未来 async 优化空间变大**

也就是说，最先感知到的通常不是吞吐量数字，而是**“终于能看懂现场了”**。

## 五、Union Type：为什么 C# 以前总缺一块拼图？

### 5.1 先问问题：我们到底想表达什么？

很多业务模型本质上都在说：

> 一个值必须是若干种可能性之一，而且就这些，没有别的。

例如：

- 支付方式只能是 `CreditCard` / `PayPal` / `BankTransfer`
- 结果只能是 `Success` / `Error`
- 参数只能是“单个元素”或“一组元素”
- 消息总线只接受若干已知消息类型

这个“**只能是其中之一**”很关键。

### 5.2 为什么 `object` 不行？

`object` 的语义是“可以是任何引用类型，值类型也能装箱进去”。

它的问题不是不能装，而是**太能装了**。

如果一个 API 返回 `object`，调用方并不知道它到底应该处理哪些合法类型，也无法获得穷尽检查。

所以 `object` 解决的是“统一承载”，不是“封闭建模”。

### 5.3 为什么接口 / 抽象基类也不够？

它们确实比 `object` 强，因为至少限制到了某一类家族：

```csharp
abstract class PaymentMethod {}
```

但问题在于：**这个集合通常不是闭合的**。

只要语言没有“闭合层次”语义，编译器就不能默认认为“只有当前这几种派生类型”。

于是 `switch` 无法真正做到：

> 我确信你已经处理完所有可能性了。

所以继承层次解决的是“共享抽象”，不是“有限全集”。

### 5.4 为什么第三方 OneOf/Result 库还是不够？

它们已经很接近 union 了，但仍然缺少语言级能力：

- 编译器不天然理解它是“闭合集合”；
- 模式匹配和 nullability 分析支持有限；
- IDE 和语法层面缺少原生体验；
- 穷尽性往往靠库 API 引导，而不是语言本身保证。

所以关键差异不是“能不能模拟”，而是：

> 编译器是否把这种抽象当成一等公民。

## 六、Union Type：语言原生支持后，到底多了什么？

### 6.1 最核心的不是“多个类型”，而是“闭合的多个类型”

```csharp
public union PaymentMethod(CreditCard, PayPal, BankTransfer);
```

这里最重要的信息不是“有三个类型”，而是：

> `PaymentMethod` 的取值空间被语言定义为这三个 case type 的闭合集。

一旦这个信息进入编译器，后面几乎所有能力都顺理成章：

- 可以有从 case type 到 union 的隐式转换；
- `switch` 可以做穷尽检查；
- nullability 可以追踪 union 内容物的 null 状态；
- IDE 可以围绕已知 case 集合给出更准确提示。

### 6.2 为什么 `switch` 能穷尽？

因为编译器终于知道“世界上合法的 case types 就这几个”。

没有这个闭合集前提，穷尽分析根本无从谈起。

所以 union 的价值，不在于它让你少写几行包装代码，而在于它把：

> “这个值的可能类型全集是什么”

变成了编译器能推理的静态事实。

### 6.3 为什么它叫 union of types，而不是传统 tagged union？

官方文档很强调这一点：C# 这次首先引入的是**type union**。

也就是说，它偏向：

- 把若干已有类型组合成一个闭合集；
- 借助现有模式匹配系统来识别具体 case；
- 不要求你必须在 union 声明里重新定义每个 case 的字段。

这和很多函数式语言里那种“在一个声明里同时定义所有 case 的数据结构”不是完全同一模型。

理解这个差异很重要，因为它解释了：

- 为什么 union 很适合复用现有类型；
- 为什么它看起来更像 C# 风格，而不是生搬硬套 F# 语法。

### 6.4 默认实现为什么用 `object? Value`？

语言参考明确说明，默认生成的 union 形态是偏“意见明确”的：

- 一个 struct
- 一个 `Value` 属性
- 内容通常存为单个 `object?`

这是一个设计取舍。

它的好处是：

- 模型简单；
- 与现有模式匹配机制容易衔接；
- 能快速覆盖绝大多数使用场景。

它的代价是：

- 值类型 case 会装箱；
- 不是所有高性能场景都最优。

这说明 union 首先追求的是**语言建模正确性与一致性**，不是默认形态就榨干一切性能。

### 6.5 为什么还支持自定义 union？

因为语言团队也知道，默认 `object? Value` 并不覆盖所有需求。

所以 C# 把“union type”和“union declaration”分开了：

- `union` 关键字是一种简洁声明语法；
- 但任何带 `[Union]` 的 class/struct，只要满足约定模式，也能被编译器当 union 对待。

这有两个深层意义：

1. **语言特性不会强迫所有人接受同一种存储布局。**
2. **已有库类型可以逐步接入 union 生态，而不是全部推倒重来。**

### 6.6 非装箱访问模式为什么重要？

如果 case types 含有 `int`、`bool` 之类值类型，而 union 又高频参与匹配，那么每次都经由 `object` 装箱/拆箱就会带来额外开销。

因此官方允许自定义 union 提供：

- `HasValue`
- 针对每个 case type 的 `TryGetValue(out T)`

这样编译器做匹配时可以走更强类型、更少装箱的路径。

这再一次说明：

> union 不是“一个固定 runtime 类型”，而是一组被语言识别并利用的模式。

## 七、Union Type：模式匹配、null、默认值，为什么容易踩坑？

### 7.1 模式匹配默认匹配的是内容，而不是 union 外壳

这是最值得单独记住的一点。

对 union 做模式匹配时，除了 `var` 和 `_` 等少数例外，模式默认作用于 **`Value`**，不是作用于 union 外层实例本身。

所以：

```csharp
pet switch
{
    Dog d => d.Name,
    Cat c => c.Name,
    Bird b => b.Name,
}
```

本质上是在匹配里面包着的内容。

这解释了为什么某些“拿 union 自己去匹配 union 类型”的写法可能不符合直觉。

### 7.2 为什么 `null` 分支经常必不可少？

因为默认生成的 union 往往是 struct，而 struct 的 `default` 值是合法存在的。此时其 `Value` 可能为 `null`。

所以哪怕 case types 都是非空引用类型，你仍然可能需要写：

```csharp
null => ...
```

来处理 union 自身默认值或内容为空的情况。

这说明 union 的 null 语义不是“case 列表里没写 null，就绝不会遇到 null”，而是要结合：

- union 是 struct 还是 class
- `Value` 当前的 null-state
- case type 自身是否可空

一起理解。

### 7.3 为什么 nullability 跟踪会增强？

因为一旦编译器知道：

- 这是 union；
- 这些是 case types；
- 当前你通过某个模式已经排除了某些情况；

它就能比普通 `object`/接口层次做更精确的 nullability 推理。

本质上，这又是“语言原生理解抽象”带来的红利。

## 八、把两者放在一起看：它们共同体现了 .NET 11 / C# 15 的设计趋势

如果只看功能点，会觉得是两个零散更新；如果看设计方向，会发现它们很一致。

### 8.1 从“编码技巧”走向“平台共识”

旧 async 本质上是编译器把高级语义编码成低级状态机技巧。  
旧 union 替代方案本质上是开发者把闭合集合语义编码成库/接口/约定技巧。

现在的变化是：

- 运行时开始原生理解异步挂起/恢复；
- 编译器开始原生理解类型闭合集合。

这意味着相关工具链都能同步收益：

- JIT / AOT / profiler / debugger / IDE / nullability analysis / pattern matching

### 8.2 为什么“一等公民”很重要？

因为只有当抽象成为平台共识，才能同时得到：

1. 正确表达
2. 静态分析
3. 调试友好
4. 运行时优化

否则你总是在某一层补丁式解决问题。

## 九、最终形成的两个心智模型

### 9.1 Runtime Async 的心智模型

可以把它理解成：

> `async` 不再主要依赖编译器把方法“翻译成状态机对象”，而是由编译器生成符合 async 协议的 IL，再由运行时原生管理挂起和恢复。

所以你看到的现象是：

- 代码写法不变
- 实时栈更像源码调用链
- 调试更自然
- 分配和保存状态的开销有进一步优化空间

### 9.2 Union Type 的心智模型

可以把它理解成：

> `union` 让“值属于固定若干类型之一”成为语言可验证事实，而不是库约定；编译器因此可以提供隐式 union 转换、穷尽匹配和更强的 nullability 推理。

所以你得到的不是“另一种花哨包装类”，而是：

- 更准确的业务建模
- 更可靠的 `switch`
- 更明确的 API 契约
- 新增 case 时的编译期反馈

## 十、几个必须记住的边界

### Runtime Async

- 目前仍是预览特性。
- 需要在项目文件中显式启用：

```xml
<PropertyGroup>
  <Features>runtime-async=on</Features>
</PropertyGroup>
```

- 它主要改善的是**实时执行期间**的调用栈可观察性。
- 并不是所有返回“Task-like”的自定义类型都自动进入 runtime async 模式，公开设计目前主要围绕 `Task` / `ValueTask` 及其泛型版本。

### Union Type

- 目前是预览特性，需要 `net11.0` 与 `LangVersion=preview`。
- Preview 3 阶段仍需手动提供 `UnionAttribute` 与 `IUnion` polyfill。
- 默认 union 形态以简单一致为优先，值类型 case 可能装箱。
- 模式匹配默认针对内容 `Value`，不是 union 外壳本身。

---

## 十一、最后的结论：为什么值得认真学，而不是只记表面用法

如果只记表面，你会得到两句不完整口号：

- runtime async：栈更干净
- union type：类似 discriminated union

这两句都没错，但都太浅。

真正该记住的是：

1. **Runtime Async 解决的是“异步挂起语义以前只能由编译器手搓状态机表达”的历史局限。**
2. **Union Type 解决的是“闭合类型集合以前只能靠库和继承约定模拟”的类型系统空缺。**
3. **二者都体现了 .NET 平台把常见高层抽象往运行时/语言底层吸收的趋势。**

一旦从这个角度理解，你以后看到更多类似特性时，也更容易判断：

- 它到底是在补语法糖，
- 还是在提升整个平台对某种抽象的原生理解能力。
