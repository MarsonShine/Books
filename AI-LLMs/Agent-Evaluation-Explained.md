# 如何评估 Agent：从一次成功到可靠交付

一个 Agent 说“已经修好了”，我们要检查什么？答案能否读懂、工具有没有报错、文件是否发生变化，都不足以单独证明任务完成。评估需要把用户目标转换成能够复核的证据，再用同样的条件比较不同版本。

[《深入理解 AI Agent》第七章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter7.md)讨论了这套过程：成功标准、评估环境与数据集、自动评分、失败诊断、选型及成本、统计判断、生产实验和训练环境。理解这些内容，可以沿着一个问题展开：**我们凭什么相信这次改动让 Agent 更可靠？** 下文用一个简化的文件整理任务解释各环节，例子和数字均为教学假设。

**先明确被测对象和成功条件。**

假设用户要求：“把下载目录中本月的 PDF 报告复制到归档目录，并告诉我处理了哪些文件。”Agent 是能根据目标调用工具、连续完成多步操作的系统。它的表现来自模型与 Harness 的配合。Harness 指围绕模型运行的程序和约束，包括指令、工具、上下文管理、执行控制与验证。

这个任务至少有三个验收条件：该复制的报告全部复制成功；原文件和其他文件不受影响；最终清单与实际处理结果一致。只检查归档目录“有文件”会漏掉少复制、复制错误和答复不实的问题。

还要明确“本月”依据报告日期还是文件修改时间。若任务本身有歧义，应把澄清列为合理行为，不能让评分器偷偷采用一种解释。这里的评分器，也称验证器，就是根据预定标准检查结果的程序或评判者。实际评估常组合代码检查、模型评分和人工复核。[Anthropic 的 Agent 评估说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)介绍了这三类评判方式及其取舍。

**让每次测试从同一个起点开始。**

一条完整用例需要写明：用户请求、初始文件、可用工具、验收条件，以及时间或操作次数上限。每次运行前恢复相同目录，否则第二个版本可能直接碰到第一个版本留下的结果。

Dataset（数据集）是一组这样的用例；Benchmark（基准测试）是在规定条件下运行的一套比较任务。可以先手写一组覆盖常见情况的文件目录，再加入同名文件、空目录、权限不足等边界情况。线上出现的新故障，经脱敏后也能转成测试用例。

涉及多轮沟通时，还需要用户模拟器，即按照给定场景回应 Agent 的程序或模型。它应该根据实际环境回答，不能因为 Agent 说“应该成功了”就表示同意。τ²-bench 的一个特色是让模拟用户和 Agent 各自拥有工具，测试双方协作改变环境的能力；它提醒我们，用户的配合也可能是任务的一部分。[τ²-bench 项目](https://github.com/sierra-research/tau2-bench)

测试题还应与调试题分开：不断针对同一批文件名修改提示词，可能只让系统记住这些例子。保留未参与调试的测试集，并变换日期、目录结构和文件内容，才能检验它是否掌握一般规则。

**分清“试出来一次”和“每次都做对”。**

Pass@k 表示同一任务尝试 k 次，至少一次成功；Pass^k 表示这 k 次全部成功。前者适合衡量探索潜力，后者关注稳定性。Best@k 则用于有连续分数的任务，取 k 次中的最高分。[Anthropic 对重复运行指标的解释](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

假设每次运行独立，成功概率都是 p，则：

```text
至少一次成功：1 − (1 − p)^k
全部成功：p^k
```

若 p = 0.8，试三次至少成功一次的概率是 99.2%，三次都成功却只有 51.2%。因此，一段挑选过的成功演示无法说明日常可靠性。真实运行还可能受同一种故障影响，并不独立；报告需要同时交代任务数量、重复次数、预算和实际结果，不能直接把公式当作保证。

对归档任务，还可以把质量拆开：精确率（Precision）关注“复制的文件中多少选对了”；召回率（Recall）关注“应该复制的文件中找到了多少”。假设应复制 8 份，实际复制了 6 份，其中 5 份正确，精确率就是 5/6，召回率是 5/8。两项都需要看，否则只复制最容易判断的一份文件，也可能获得很高的精确率。

**根据证据选择评分方法。**

文件内容是否一致可以用程序比较；解释是否清楚则适合用 Rubric——事先写好的评分细则。例如，“列出全部成功复制的文件；区分失败与跳过；不要把未验证的结果说成完成”，比“回答专业、完整”更容易执行。

LLM-as-a-Judge 是让语言模型依据这些细则评分。它适合开放式回答，但评分本身也需要校准：抽取样本让人复核，检查它是否偏爱冗长答案，交换两个候选答案的展示顺序，看结论是否改变。多个模型的意见可以辅助审计，但不能保证它们没有共同盲点。[Anthropic 的模型评判实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

同样的方法可以扩展到多模态产物，即包含文字之外的声音、图像或视频。评估语音自然度需要听音频，检查界面遮挡需要看渲染结果；单靠转写文本或生成者的描述，会丢掉需要评分的信息。

还要防止“高分捷径”：如果只按答复是否包含“已完成”评分，Agent 即使没有复制文件也能通过。这类满足评分规则却偏离真实目标的行为称为奖励作弊（Reward Hacking）。验证器应有独立证据，尤其不能让被测 Agent 随意修改决定自己是否通过的检查规则。

**失败以后，沿证据寻找最早的偏离。**

设想归档结果少了三份文件。可能是枚举工具漏掉了子目录，也可能是工具返回完整、模型筛选错误，还可能是复制失败后答复仍声称成功。三种情况分别需要检查观察工具、决策逻辑和完成验证。

这需要可观测性（Observability）：通过运行记录理解系统发生了什么。Trace 是一次任务的完整追踪；Span 是其中一次模型请求、工具调用或检索等操作，保存起止时间和相关信息，父子关系把操作串起来。[OpenTelemetry 对 Trace 与 Span 的定义](https://opentelemetry.io/docs/concepts/signals/traces/)

例如，记录“枚举返回 8 份 → 模型选中 5 份 → 复制成功 5 份 → 答复称全部完成”，就能把筛选遗漏和完成声明错误分别定位。日志只写“复制成功”则无法解释全任务为何失败。保存时还应记录版本、输入条件和证据引用，敏感内容按需脱敏。

修复后需要回归测试，即检查旧问题没有再次出现。原章区分了两种互补方式：端到端回归从头完成任务；轨迹前缀回归恢复到错误发生前的上下文和环境，只检查接下来的决策。[第七章：回归任务](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter7.md)

在上述例子中，前者重新运行整次归档，后者直接提供“工具返回 8 份报告”的状态，看 Agent 是否正确筛选。允许多种正确操作顺序，但必须检查遗漏和禁止行为。

**比较版本时，把质量、时间、费用放在一起。**

Model swap（模型替换实验）固定其余条件，只更换模型；Ablation（消融实验）关闭某个组件，检查它的贡献。两者用来缩小原因范围。更强模型未提分只是一个线索，还可能涉及样本太少、适配问题或任务已经接近满分，不能据此断定某个组件就是根因。

比较费用也要用完整任务。假设方案 A 每次花 0.02 元、100 次成功 50 次；方案 B 每次花 0.03 元、100 次成功 90 次。那么本批次每次成功对应的总费用分别是 2/50 = 0.04 元和 3/90 ≈ 0.033 元。这个口径包含失败的花费，更接近交付成本；若还需要人工补救，也应计入。

时间指标各有含义：TTFT（首个 token 的等待时间）反映模型开始输出的速度；端到端延迟是从提出任务到交付结果的总时间；吞吐量是单位时间内处理的工作量。Token 是模型处理文本等输入输出的计量单位，不等同于汉字数。对于会先内部推理的系统，首个可见字还可能要等待推理完成。

p95 延迟是一个百分位数：约 95% 的观测值不超过它。平均 10 秒不能排除少数任务耗时一分钟，因此需要同时看平均值和尾部延迟。预算也要固定：允许一分钟和允许十分钟的成功率，不能直接比较。

排行榜中的 Elo 是通过两两胜负更新的相对评分方法；Bradley–Terry 模型则用潜在能力差描述两两胜率。它们能整理偏好数据，但偏好排名不等于归档成功率，仍需回到自己的任务验证。

**小分差需要更多证据，改动需要逐步发布。**

假设两版在同一批任务上分别通过 40/50 和 42/50。多做对两题值得检查，却还不足以保证在新任务上更好。配对分析会逐题比较：新版本修好了哪些，又破坏了哪些；重复运行则帮助观察模型自身的波动。

统计显著性检验是在一定假设下判断观察到的差异是否可能由随机波动造成。置信区间用一个范围表示估计的不确定性；它不是对每次运行的成功保证。初学时最实用的做法是保留逐题结果、重复测量，并对很小的分差保持审慎。只反复运行同一道题也不能替代增加不同任务。

离线测试通过后，可以用 A/B 测试把真实用户随机分组，对比新旧版本。Feature Flag（特性开关）控制哪些用户启用改动，也支持快速关闭。提示词与程序一样要有版本记录，才能知道哪个变化对应哪组结果。

这里要区分目标和手段。例如，“减少目录查询次数”是改动手段；真正目标可能是缩短归档时间。如果省掉查询导致漏文件，手段达成了，目标却没有达成。成功率等不能恶化的条件称为护栏指标。发布判断应同时检查目标收益和护栏。

**评估环境还可以成为训练环境。**

原章最后把评估连接到后训练：模型完成初始训练后，可以继续利用任务反馈改进行为。强化学习中的奖励是行动结果的反馈分数；RLVR 指使用可验证奖励的强化学习，例如由独立程序判定文件是否正确归档。模型给出的主观分数并不会自动变成可靠的可验证奖励。[第七章：仿真与后训练](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter7.md)

用于反复练习时，环境需要快速重置和并行运行。一个 Episode 是从初始状态到任务结束的一轮交互。领域随机化是在练习中变化目录、文件数量、响应延迟等条件，帮助系统适应陌生情况；仿真与真实环境之间仍可能有差异，最终还需真实场景验证。

对文件归档系统，可以先建立几条需求明确的任务，保存完整轨迹，找出第一处遗漏，修复后同时跑局部和完整测试，再观察真实用户中的效果。随着这些证据逐渐积累，“要不要换模型、加工具或改提示词”才有了可比较的依据。
