# 第七章读书笔记：Agent 的评估

阅读来源：[《深入理解 AI Agent》第七章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter7.md)。整理日期：2026-09-08。

Agent 能完成一次任务，说明它具备某种能力；能在不同任务、不同环境下稳定完成，才说明它值得使用。评估要把这种区别测量出来，并提供足够证据，解释系统为什么成功或失败。

**1. 评估对象是完整系统，成功标准必须来自任务**

Agent 的结果由模型、输入信息、工具和执行机制共同决定。Harness 就是围绕模型建立的运行系统，负责组织上下文、执行工具、维护状态和检查结果。模型本身足够强，如果没有获得必要信息，依然可能失败。

例如，要求 Agent 把图片中的数据录入表格，而运行系统只提供页面文字、没有提供图片，错误首先来自观察通道。换模型未必有用。这也是评估必须保存中间证据的原因：最终失败看起来相同，修复方向却可能完全不同。

成功通常包含三件事：**结果正确、过程符合约束、反馈与实际一致。** 客服实际退了 100 元，却告诉用户退了 200 元，属于“操作正确、告知错误”；删除失败的测试后得到全绿，属于“表面通过、过程违规”。单一总分容易掩盖这些差别。

**2. Pass@k 测能力上限，Pass^k 测重复运行的可靠性**

模型的输出具有随机性，同一个任务重复执行，结果可能不同。因此“成功率”必须说明尝试次数和统计口径。

| 指标 | 判定方式 | 回答的问题 |
| --- | --- | --- |
| Pass@1 | 一次尝试是否成功 | 单次交付有多可靠？ |
| Pass@k | k 次尝试中至少一次成功 | 多给几次机会，能否找到正确解？ |
| Pass^k | k 次尝试全部成功 | 能否反复做对？ |
| Best@k | k 次尝试中的最高分 | 有筛选机制时，最好能做到什么程度？ |

如果每次尝试独立，且成功概率都为 p，则：

```text
Pass@k = 1 − (1 − p)^k
Pass^k = p^k
```

假设 p = 80%，尝试三次至少成功一次的概率是 99.2%，三次全部成功只有 51.2%。这解释了为什么漂亮的演示与可靠的产品之间仍可能有很大距离。[Agent 评估中的重复运行指标](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

两种指标各有用途。探索程序解法时，可以运行多次并用测试筛选；执行不可随意重复的业务操作时，则更关心每一次是否正确。公式建立在独立、同分布的假设上，实际故障可能相关，不能把公式计算值直接当作线上保证。

**3. 评估环境让“再测一次”具有可比性**

完整评估包含五部分：任务数据、初始环境、工具、评分规则和交互协议。交互协议规定谁先行动、怎样结束，以及最多允许多少轮或多少时间。

环境必须能恢复到明确的初始状态。否则第一次已经修改了数据库，第二次就可能因为前一次的残留而轻易通过。沙盒是与真实业务隔离的执行环境，适合重置数据、重复运行和观察副作用。

人机交互任务还需要用户模拟器。它不能一开始就知道全部故障原因，也不能凭空确认问题已经解决。τ²-bench 的双控环境让 Agent 操作业务系统、模拟用户操作自己的设备，两边各有信息与工具。这里测试的还包括 Agent 能否通过沟通获得缺失信息。[τ²-bench 项目](https://github.com/sierra-research/tau2-bench)

**4. 数据集要覆盖真实任务，也要防止“会做考题”**

Dataset 是评估用例的集合；Benchmark 是任务、环境和评价口径相对统一的一套基准。不同基准考察不同能力，数字不能脱离任务比较。

| 基准 | 主要任务 | 值得关注的验证思路 |
| --- | --- | --- |
| τ²-bench | 客服沟通与工具操作 | 对话之外还检查环境变化 |
| SWE-bench Verified | 修复代码问题 | 既验证新问题修好，也验证旧功能未坏 |
| AndroidWorld / OSWorld | 操作手机或桌面 | 检查应用和系统的实际状态 |
| Terminal-Bench | 终端中的工程任务 | 运行程序并检查产物 |
| GAIA | 搜索、阅读和计算的组合任务 | 按任务答案验证综合结果 |

这些基准的用途与设计比较见[原章的评估数据集部分](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter7.md)。

自建数据集通常结合公开任务、真实业务任务和线上失败案例。除了简单题，还要有多步依赖、歧义、工具故障和规则边界。按任务类别分别统计，才能看到总分掩盖的薄弱环节。

数据泄漏指评估答案或轨迹提前进入训练、调试过程，使分数高估了对新问题的能力。参数化任务、隐藏测试、独立留出集都能降低这种风险。留出集就是没有参与训练或调优的数据；只改姓名而保留完全相同的解法，仍不能保证真正独立。

**5. 验证器的关键，是检查能够独立复核的事实**

能写成程序检查的条件，优先用程序：金额是否正确、文件内容是否一致、测试是否通过。程序化验证也能检查过程，并非只能检查终态；其覆盖范围取决于我们具体写了什么。

代码修复可以拆成两组测试：FAIL_TO_PASS 检查原本失败的测试是否通过，PASS_TO_PASS 检查原本正常的测试是否仍通过。前者证明修复有效，后者防止回归——即新改动破坏已有能力。即使两组都通过，也只能证明测试覆盖的性质，而不能证明绝对无缺陷。

开放式任务缺少唯一答案，可以使用 LLM-as-a-Judge，即让模型依据评分标准评判。Rubric 是把“好不好”拆成可操作条目的评分细则，例如“关键结论有来源”“没有编造数值”“明确说明未完成事项”。事实准确性、完整性和表达质量应分开判断。[评分器的类型与取舍](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

评分模型也可能偏爱长回答、偏向先展示的候选，或与被测模型具有相同盲点。可以交换展示顺序、抽样人工复核、用不同评判者检查分歧。多模态任务还要提供相应证据：评价声音自然度必须听音频，评价界面是否遮挡必须看实际界面。

只优化分数可能产生奖励作弊：模型满足了评分器的漏洞，却没有完成用户目标。因此验证器和验收条件不能由被测 Agent 随意修改。

**6. 失败归因要找出最早有证据的偏离**

轨迹是一次任务中观察、决策、工具调用与结果的记录。失败归因就是沿轨迹解释错误如何发生，区分起因和连锁后果。

“工具调用失败”可能是错误参数造成的，也可能是服务暂时不可用；“模型没有读懂图片”可能实际是图片从未进入上下文。定位时要逐步对照：系统提供了什么，模型依据什么行动，工具实际做了什么。

一个有用的归因记录应包含任务、首个关键错误、证据位置、原因判断和不确定性。多因素共同作用时可以保留多个原因，不能机械地把时间上最早的异常当作唯一根因。

修复后需要两类回归任务：

- **端到端回归**：从用户请求开始跑完整流程，检验最终交付。
- **轨迹前缀回归**：恢复到错误决策之前的上下文和环境，专门检验下一步是否改善。

例如“没有测试就宣布完成”，可以把“代码已改、测试未运行”设为固定起点。正确动作可以有多个，但必须继续验证，不能只换一种措辞宣称成功。[原章的失败归因与回归任务](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter7.md)

**7. 实验区分原因，统计判断区分改善与波动**

模型替换实验固定 Harness，只换模型；消融实验保留其他条件，关闭一个组件。前者观察模型因素，后者观察组件贡献。若一次更换没有提分，只能缩小调查方向，还要排除样本不足、适配差异或任务已接近满分等解释。

同一批任务比较新旧版本，宜逐题配对。比如总分都为 80%，可能一个版本修好了十道题，却又破坏了另外十道。总分相同不等于行为相同。

测得成功率为 p、独立样本数为 n 时，其标准误可粗略估计为：

```text
SE ≈ √[p × (1 − p) / n]
```

标准误描述估计的抽样波动。假设 100 题中成功 70 题，正态近似下的 95% 置信区间约为 70% ± 9 个百分点；小样本或接近全对、全错时，应使用更合适的区间方法。置信区间反映估计不确定性，不保证下一次测试落在其中。

新旧版的差异还要做配对分析，不能仅凭两个区间是否重叠下结论。McNemar 检验关注两版“一个对、一个错”的任务；配对 bootstrap 则反复重采样任务对，估计分差波动。对同一道题重复采样不能当作新增独立题目；反复试很多方案后挑最高分，也需要独立复测以排除偶然胜出。

**8. 模型选型比较的是完成任务的总成本**

Token 是模型处理输入输出的计量单位。单价低不等于交付便宜：失败重试、工具服务和人工补救，都应计入总成本。

模型推理通常包含 Prefill（处理输入上下文）和 Decode（逐步生成输出）。TTFT 表示首个 token 的等待时间；端到端延迟包括模型、工具和环境等待；吞吐量表示单位时间处理多少工作。p95 是约 95% 的观测值不超过的延迟，可帮助发现平均值掩盖的长等待。

多轮任务中，历史和工具返回可能被反复输入，累计费用明显高于单轮。前缀缓存复用已处理内容，压缩减少输入长度，但压缩也可能改变可缓存前缀，两者收益不能简单相加。选型应比较相同预算下的成功率，以及多个预算点上质量如何变化。

**9. 可观测性把评估嵌入日常改进**

Trace 表示一次任务的整体追踪，Span 表示其中一次模型调用、工具操作或检索，记录时间、输入输出和错误。OpenTelemetry 提供了通用追踪概念，便于把采集与分析系统分开。[Trace 与 Span](https://opentelemetry.io/docs/concepts/signals/traces/)

持续改进可以依次进行：发现集中失败的任务，核对评估环境，提出一个可测试的原因假设，修改相关组件，运行局部与全量回归。小范围改善只支持扩大测试，不能直接宣称系统全面提升。

上线后，A/B 测试通过随机分流比较新旧版本；特性开关控制功能是否启用，便于渐进发布和关闭。实验要分清机制指标、目标指标和护栏指标：缩短计划是机制，降低总成本是目标，成功率不能下降是护栏。提示词也应记录版本，线上轨迹经脱敏后再回流成用例。

评估环境进一步用于训练时，还要提高重置速度、并行能力和反馈质量。验证器可以成为奖励来源，但用于训练的任务与最终评估任务必须分开，才能知道模型学到的是可迁移能力，还是熟悉考题的捷径。
