# Agent 的持续进化：怎样让经验改善下一次任务

归档助手今天漏掉了一批没有日期的报告。用户指出后，它补查正文，完成了任务。明天遇到同样情况，它是否会主动补查？这取决于系统有没有把这次经历转换成后续可用的改进。

[《深入理解 AI Agent》第九章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter9.md)将这种系统层面的改进称为持续进化。它既可以更新知识、指令与程序，也可以使用[后训练](Model-Post-Training-Explained.md)更新参数。本篇沿用文件归档的教学例子，解释经验从记录到生效的过程。

**当前任务中的适应，需要一条通向未来的路径。**

模型可以根据上下文中的纠正改变下一步行动，但普通推理并不更新模型权重。把对话存起来，也只是让未来有机会检索到它。要使下次操作更可靠，还需要找出可复用的判断，并验证其适用范围。

比如，“周报 A 的日期是 9 月 3 日”是一个事实；“文件名没有日期时，先检查正文中的报告期”是一种操作经验。后者还缺少边界：正文中的签字日期、导出时间未必是报告期。如果不处理这些差异，一次成功做法可能变成下一次错误。

Reflexion 展示了用语言反馈和经验记忆调整后续尝试的方法，无需每次更新模型参数。它提供了一条可行路径，但模型生成的反思仍需要与实际执行证据核对。[Reflexion 论文](https://arxiv.org/abs/2303.11366)

**先评价经历，再提炼规则。**

可以为每次归档保留三个层次的检查：目标文件是否全部处理，操作是否遵守保留原文件等约束，答复是否准确清楚。一句“用户满意”无法替代这些检查；用户也可能尚未发现错误。

记录应能回答：“遗漏发生在哪一步？当时工具返回了什么？哪些判断有证据？”如果读取工具没有返回报告正文，问题在观察通道；如果正文已有报告期而模型仍忽略它，问题才可能在筛选策略。两者需要不同的修复。

提炼时还要同时看成功和失败。假设十次任务中，有八次从正文找到报告期，两次正文包含多个日期而判断错误，那么候选经验应包含歧义处理，不能只保留八次成功。证据不足时，可以暂存为待验证假设。

**根据问题性质决定改在哪里。**

| 更新位置 | 归档任务中的例子 | 为什么放这里 |
| --- | --- | --- |
| 经验知识库 | 某部门报告期通常写在封面右上角 | 需要来源、适用部门与版本，可按需检索 |
| Prompt / Skill | 找不到报告期时的查询与澄清原则 | 需要理解语境及例外，可用语言描述 |
| 程序 / Harness | 复制前检查目标文件是否已存在 | 可明确执行并自动测试 |
| 模型参数 | 在多种版式中稳定识别报告期 | 若现有模型能力不足，可考虑专门训练 |

Prompt 是指导模型的输入指令；Skill 是按任务加载的专门说明或操作资源；Harness 是组织模型、工具、状态和执行约束的运行系统。知识告诉模型可参考什么，指令指导它如何判断，程序保证约定的检查实际执行。

这些位置可以配合。例如，知识库记录报告模板，Skill 解释多个日期如何取舍，程序校验日期格式，而模型负责识别图文内容。更新参数也不是唯一办法；如果已有工具能可靠提取日期，接入工具可能更直接。

**经验成为程序时，要保存条件和验证。**

假设助手已反复完成“读取报告 → 提取报告期 → 生成归档路径 → 复制 → 核对清单”。稳定部分可以写成参数化工作流：把固定的月份、来源目录和目标目录换成输入参数，以后直接运行。

这类似把手工操作整理成脚本。工作流仍要检查前置条件、每步结果和最终清单；仅仅重放点击顺序不能证明复制成功。模板或工具接口改变后，应暂停这条失效流程，再重新探索。

Voyager 在 Minecraft 中把经过环境反馈改进的程序保存为可复用技能，并根据已有能力选择新目标。它把课程安排、技能库和迭代执行结合起来，说明可执行经验能够被积累和组合。[Voyager 论文](https://arxiv.org/abs/2305.16291)

应用到归档场景，提案可以是一小段程序修改：“缺失日期时输出待处理清单”，而不是让助手直接改写全部业务逻辑。提案需要同时声明预期改善和可能影响的旧行为，方便用测试推翻错误假设。

**执行与改进使用不同的循环。**

在线执行循环负责当前任务并记录结果；离线改进循环集中读取经过评价的经历，提出候选修改，再运行独立测试。这里“离线”指不直接改变正在服务用户的正式版本，不要求断网，也不要求一定在夜间执行。

```text
任务执行并留证 → 对照多次经历 → 提出局部修改
       ↑                         ↓
   使用已发布版本 ← 小范围发布 ← 独立测试
```

例如，先在缺失日期的任务上验证修复，再检查原本正常的任务，确认新规则没有让每份报告都多问一轮。回归测试就是检查改动后已有能力是否退化；留出任务是未参与经验提炼的测试任务，用来检验经验能否迁移。

通过后可以灰度发布，即先让少量任务使用新版本，并保留回滚能力。回滚是恢复旧的运行版本，不一定能撤销已经复制、发送或修改的数据，实际操作结果仍需另行处理。

**“写出改进”和“用上改进”要分别检查。**

假设新 Skill 已经准确解释报告期，却没有被检索到。最终成绩不变，不能因此断定经验无效；如果每次都加载，却仍按旧策略行动，问题又在应用环节。

因此可以分别观察：提案通过验证的比例、正确场景中加载产物的比例、加载后遵循规则的情况，以及新任务的质量和成本。它们把“没有进步”拆成可处理的问题。[第九章关于更新与受益能力的区分](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter9.md)

更进一步，系统还可以调整产生改进的方法。例如从“只看失败摘要”改为“同时比较原始证据、成功案例和历史被拒提案”。这是在优化更新器，影响范围更大，测试应覆盖多个任务族，不能只在触发修改的那几个例子上评分。

**长期经验需要修订和淘汰。**

新报告模板上线后，旧的封面位置规则可能失效。经验条目应带上来源、适用范围、版本和最近验证时间。重复项可以合并，冲突项需要对照证据，过期项退出默认检索，同时保留审计与恢复记录。

“睡眠学习”可以理解为这类后台整合：积累一批经历后，再更新索引、去重和验证。它不表示模型像人一样入睡，也不表示每晚必须微调一次。当前指令与旧经验冲突时，系统还应检查适用范围，不能让旧习惯覆盖用户的新要求。

生成建议的模块也不应自行降低验收标准。网页和工具返回中可能夹有误导指令，模型把它们总结一遍不会自动变成可信规则。证据来源、正式能力库与批准更新的机制，需要保持明确边界。

开放式任务尤其困难。例如“归档是否完整”可以核对清单，而“调研是否有价值”缺少同样明确的终点。此时要保留失败实验和不同方向的候选方案，由人审查问题与评价标准，避免系统只越来越擅长迎合自己的评分器。

对归档助手，值得发布的经验应当能解释何时使用、由哪些结果支持、怎样验证和何时失效。这样的经验才能在下一次任务里减少错误，而不只是增加一份更长的日志。
