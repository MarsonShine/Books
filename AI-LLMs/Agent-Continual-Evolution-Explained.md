# 第九章读书笔记：Agent 的持续进化

阅读来源：[《深入理解 AI Agent》第九章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter9.md)。整理日期：2026-09-08。

Agent 今天解决了一个难题，明天仍可能在相似任务里从头试错。原因是，执行经历不会自动变成新能力。持续进化需要主动评价经历、提炼可复用规律，选择合适的更新位置，并验证这些更新确实改善了后续行为。

**1. 记忆、任务内适应和持续进化是三件事**

任务内适应发生在上下文中：用户纠正后，模型利用这条信息改变下一步。普通推理不会更新权重，因此新会话能否继续受益，取决于信息是否被保存并重新提供。

长期记忆保存可以重新检索的事实与经历。它解决“还能不能找到”，但没有自动解决“这次经验是否正确”“是否适用于当前任务”。一份长日志可能同时包含有效做法、错误尝试和偶然成功。

持续进化多了一层主动加工：比较多次执行，判断哪些规律值得保留，再把规律变成知识、指令、程序或参数更新。反思可以产生假设，环境结果才提供检验假设的证据。Reflexion 展示了利用语言反馈与经验记忆改善后续尝试的路线，而不要求每次更新权重。[Reflexion 论文](https://arxiv.org/abs/2303.11366)

可以把三者分别理解为：**当前想得更对、以后记得起来、以后更稳定地做对。**

**2. 一条轨迹怎样变成学习信号**

轨迹是一次任务中输入、动作、工具返回和结果的记录。判断其价值，需要分开检查三个层次：

| 层次 | 要确认什么 | 主要证据 |
| --- | --- | --- |
| 结果 | 目标是否实际达成 | 测试、数据库、文件或界面状态 |
| 过程 | 是否遵守任务约束和权限 | 操作序列、规则、访问记录 |
| 质量 | 解释是否清楚，交互是否恰当 | 回答内容、用户反馈与评分细则 |

三层不能互相替代。客服表达得很耐心，不代表退款已发生；结果正确，也不能抵消泄露信息或虚假承诺。Rubric 是逐项说明如何评价的评分细则，适合辅助判断难以完全写成代码的质量问题。

可用于学习的记录应说明成功或失败、具体问题、证据位置和适用条件。证据不足时，应保留不确定性，而不能让一个自信的模型评分直接成为事实。

提炼还要看到成功与失败的对照。一次成功可能因为环境恰好宽容；一次失败也可能只是网络波动。只从单条轨迹下结论，很容易把偶然现象变成长期规则。

**3. 四种更新方式对应不同性质的经验**

| 更新载体 | 适合保存什么 | 主要边界 |
| --- | --- | --- |
| 经验知识库 | 事实、策略经验、例外和来源 | 找到后仍需模型正确理解与应用 |
| Prompt 与 Skill | 能用语言表达的判断原则、流程与优先级 | 可能冲突、膨胀或被忽略 |
| 程序与 Harness | 可明确执行的流程、检查和限制 | 需要维护、测试与版本管理 |
| 模型参数 | 难以逐条描述的感知、表达和隐式策略 | 更新昂贵，可能影响旧能力 |

Prompt 是提供给模型的指令；Skill 是按任务加载的专门规则与资源；Harness 是组织模型、工具、状态和执行控制的运行系统。四种载体是配合关系，不是从低级到高级的升级路线。[原章的四类更新方法](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter9.md)

例如，“接口的新地址”适合进入知识或配置；“缺少用户编号时先询问”适合表达为指令；“没有编号就禁止发请求”可以由程序保证；“从不同表达中识别用户意图”可能需要已有模型能力或参数训练。

判断位置时，应问“这条经验能否被准确表达和验证”，而不只是“它会不会长期稳定”。能用几行程序可靠完成的检查，没有必要每次让模型重新判断。

**4. 经验知识需要条件，而不只是摘要**

有用的经验单位应包含：什么情况下使用、建议做什么、为什么、有哪些例外、证据来自哪里、对应什么版本。

比如“遇到错误就重试”过于宽泛。更有用的经验是：临时服务故障可以有限重试；权限错误应先检查权限；参数缺失需要补参数。差别在于，后者把动作与原因连接起来。

经验提炼可以保留三层：原始轨迹用于追溯，单次分析解释本次结果，正式经验汇总多条记录的共性。正式经验不必保留所有试错细节，但应能沿引用回到原始证据。

知识是否有效，最终看未参与提炼的新任务。换一种问法、换一个接口版本就失效，说明经验可能只记住了表面模式。

**5. 把经验提升为指令，要限制作用范围**

系统 Prompt 通常对广泛任务生效，局部经验更适合进入领域 Skill。把所有例外不断追加到全局提示中，会增加相互冲突，也会使真正重要的原则难以被找到。

一个典型问题是澄清需求。每个小改动都追问，会造成打扰；涉及关键选择时不问，又容易返工。可学习的规则应说明触发条件，例如缺失信息会改变实现方案时才集中提问，而不是“总要问”或“永远直接做”。

自动提示优化可以生成候选指令，在开发集上比较效果，再用独立任务验证。DSPy、OPRO、GEPA 代表了从示例、得分或失败反馈搜索提示的不同路线；它们需要有效评价标准，不能仅凭提示看起来更完整来判断优劣。

发布时同时检查边界任务和保留任务：前者覆盖新发现的问题，后者覆盖原本正常的行为。修好了歧义处理，却让所有简单请求多出几轮询问，仍然可能降低整体质量。

**6. 稳定操作可以沉淀为可执行工作流**

工作流是带输入、步骤和检查条件的程序化流程。第一次操作陌生网站时，Agent 需要探索；流程稳定后，可以把可复用部分参数化，把收件人、文件名等具体值变成变量。

可复用流程至少要检查三件事：

- 执行前：当前页面、权限和输入是否满足条件。
- 执行后：这一步是否产生预期变化。
- 完整回放后：最终业务结果是否成立。

“点击没有报错”只能证明动作被执行，不能证明任务成功。页面改版、接口变化或状态检查失败时，应让流程失效，回到重新观察和规划，而不是继续盲目回放。

Voyager 将环境中练习得到的程序保存为技能库，并根据已有能力安排新的学习目标。技能可检索、可组合，环境反馈用于继续修正，这使一次成功能够成为后续任务的基础。[Voyager 论文](https://arxiv.org/abs/2305.16291)

模型修改自己的运行代码，也应产生一个待验证版本。局部补丁需要说明失败证据、原因假设、预期改善和可能受损的行为。曾被拒绝的提案也值得保存，避免系统反复探索同一条失败路径。

**7. 改进运行系统，还需要管理依赖和生命周期**

工具与模型适配器经常以插件形式组织。动态更新插件时，要同时处理两种关系：它改变了哪些状态，以及它依赖哪些组件。

例如，插件注册了一个事件监听器；卸载时不移除监听器，就可能重复处理事件。插件依赖的工具接口改变后，也必须重新检查兼容性。组件能够安装，不等于能够安全撤销或替换。

可撤销的运行时资源与不可撤销的业务副作用还要区分。关闭插件可以释放连接、移除注册，但不能自动撤回已经发送的邮件。动态组合提高更新灵活性，不会取消外部验证和发布流程。

当目标变成改进检索器、上下文整理器，甚至生成更新提案的程序时，系统正在学习“怎样改进”。影响范围随之扩大：修改一条经验可以用少量边界任务检查，修改整个经验筛选机制则需要多类任务和长期数据。

**8. 在线执行与离线进化通过版本连接**

在线循环优先完成用户任务并记录证据；离线循环聚合已评价的经历，形成更新提案并测试。离线不是断网或只能夜间运行，而是将长期能力更新与当前业务执行解耦。

```text
正式版本执行 → 保存轨迹 → 评价与对照 → 候选更新
     ↑                                  ↓
发布或回滚 ← 独立测试与小范围验证 ← 隔离试运行
```

这样一次偶发失败不会立即改写所有任务的行为，也能对新旧版本做公平比较。回滚恢复的是系统版本；更新期间发生的外部操作，需要按业务情况另外恢复。

**9. 更新有效，与任务 Agent 能受益，需要分别验证**

一份 Skill 写得正确，却可能没有被检索到；被加载后，也可能没有被遵循。因此评估要沿着“提案 → 激活 → 执行 → 结果”逐层观察。

可以分别记录提案的独立验证结果、正确场景中的加载率、加载后的执行情况，以及新任务的质量、成本和旧能力保持情况。端到端分数没变时，这些记录才能解释瓶颈在哪里。[原章对更新能力与受益能力的区分](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter9.md)

参数更新同样遵循这个逻辑：可靠示范可用于监督微调，偏好对可用于偏好优化，具有环境奖励的轨迹可用于强化学习。但外部知识与程序依然可以承担事实更新和确定性约束。

**10. 长期进化还包括遗忘、淘汰和独立监督**

经验不断增加，会出现重复规则、过期工具和互相矛盾的结论。“睡眠学习”是后台整合这些内容的类比：批量回顾、合并、检查适用条件、更新索引，并把失效条目移出默认使用范围。保留来源与历史版本，才能在错误整理后恢复。

证据与指令也要隔离。网页中的一句恶意命令，即使被摘要成“经验”，仍不应成为正式规则。总结并不能把不可信输入自动变成可信知识。

提出修改的 Agent 不能通过降低验收门槛来批准自己。验证器、发布规则和审计依据需要独立保护；验证器本身当然也可能有错，但应由另一套审查过程修正。

开放式科研等任务还面临目标难以评分的问题。保留负面结果、保持多种候选方向、让人检查问题与评价标准，可以减少系统只迎合评分器的倾向。一次更新被接受，只说明更新流程通过；后续任务持续变好，才是进化产生价值的证据。
