# Computer Use Agent 的观察接口：从关键帧到事件驱动的多速率感知

Computer Use Agent 最早采用的思路很直观：截一张屏幕截图，让模型决定下一步，再执行一次点击或输入，然后重新截图。

这个思路隐含了一个前提：屏幕在两次截图之间基本是静止的。但现实中的电脑并不是一组静态图片。页面会加载，视频会播放，通知会弹出又消失，会议会有人讲话，鼠标和窗口也在持续变化。如果 Agent 每次检测到像素变化，都走一遍“截图 → OCR → 语义理解 → 更新上下文 → LLM 推理 → 操作”，它当然会慢到无法使用。

所以真正需要重新设计的，往往不是动作接口，而是观察接口：Agent 怎样持续感知一个高速变化的电脑环境，又怎样只把值得处理的变化交给昂贵的推理模型？

本文沿用聊天记录中的 AOI（Agent Observation Interface）这个概念，指位于电脑环境和 Agent 之间的观察层。这里的 AOI 是一种工程架构概念，不表示某个厂商已经公开确认的内部实现。

## 一、先把“屏幕变化”和“需要推理”分开

一个容易产生误解的模型是：

```text
屏幕变化
    ↓
截图
    ↓
OCR
    ↓
语义解析
    ↓
更新 Context
    ↓
LLM 推理
    ↓
执行操作
```

如果鼠标移动一个像素、加载动画改变一帧、按钮出现一次 hover 效果，都触发这条链路，系统必然会被模型调用拖垮。

真正可用的系统需要把两个问题分开：

1. 环境有没有发生变化？
2. 这个变化是否足以让 Agent 重新做决定？

第一个问题可以由本地程序、浏览器事件、传统视觉算法或小模型高频处理；第二个问题才需要升级到视觉语言模型或通用 LLM。

因此，Agent 的循环不是“每个变化都推理”，而是：

```text
持续观察环境
      ↓
筛选并聚合变化
      ↓
形成语义状态或事件
      ↓
是否到达决策边界？
      ├─ 否：继续本地处理
      └─ 是：调用模型重新规划
```

可以把它概括成三个动作：

> **持续捕获，选择理解，稀疏推理。**

## 二、AOI 到底是什么

传统 Computer Use 更像是：

```text
Agent 主动截图 → 模型理解 → Agent 操作
```

AOI 则把观察变成一个独立的运行时层：

```text
电脑环境
    │
    ├─ 屏幕与窗口
    ├─ 音频与麦克风
    ├─ 浏览器 DOM / Accessibility Tree
    ├─ 鼠标、键盘和系统通知
    ├─ 文件系统和网络状态
    │
    ▼
Observation Runtime
    │
    ├─ 变化检测
    ├─ 关键帧采样
    ├─ VAD / ASR
    ├─ 状态估计
    ├─ 事件聚合
    ├─ 视觉与多模态摘要
    │
    ▼
统一 Observation Event
    │
    ▼
Agent / LLM
```

AOI 不会把 60 FPS 的视频、连续音频和所有原始截图一股脑塞进模型上下文。它先把连续输入转换成数量更少、语义更稳定的离散事件。

例如，模型最终看到的可以是：

```text
Event #101
type: screen
time: 14:02:01
content: Chrome 打开了 GitHub Issues 页面。

Event #102
type: audio
time: 14:02:04
content: 参会者说：“修一下第二个 bug。”

Event #103
type: screen
time: 14:02:06
content: 第二个 Issue 已打开，标题为 Login timeout。
```

Agent 处理的是事件流，而不是原始视频流。这样做同时解决了三个问题：减少观察盲区、避免上下文爆炸、补齐音频等缺失模态。

## 三、屏幕关键帧：像素变了，不代表语义变了

最简单的关键帧策略是比较相邻画面的像素差异：变化超过阈值，就保存一张新截图。但这种方法只能回答“画面变了吗”，不能回答“对任务来说发生了什么”。

两个反例很典型：

- 广告 GIF 不断播放，像素变化很大，但页面的任务语义没有变化；
- “支付成功”四个小字出现，像素变化很小，但对 Agent 来说是关键事件。

因此，观察层至少要区分三种变化：

```text
Pixel Change
    ↓
Visual / UI Change
    ↓
Semantic Change
```

它们的含义分别是：

- 物理变化：像素、光流或局部区域发生变化；
- 视觉变化：页面内容、窗口、控件或对象发生变化；
- 语义变化：任务状态、可执行动作或环境含义发生变化。

对应到常见 GUI 场景：

```text
鼠标移动                  → 通常忽略
按钮 hover                 → 通常忽略
加载 spinner 转动          → 通常忽略
图片逐渐加载               → 通常忽略或合并
按钮从禁用变为可点击       → 记录
页面发生导航               → 记录
弹出错误提示               → 记录
出现验证码或确认框         → 高优先级记录
页面显示操作成功           → 记录
```

所以“每秒截图 1 次”只能理解成某些 GUI 场景下的经验性采样策略，不能理解成普遍规则。静态表单、网页导航和办公软件可能不需要高帧率；视频分析、拖拽、动画交互或需要捕捉瞬时内容的任务则可能需要更密集的采样。

更好的关键帧检测器，应该结合像素差、控件变化、页面结构变化和任务目标，而不是单独依赖 MSE、SSIM 或简单的 frame diff。

## 四、音量门控：给 Computer Use Agent 加上耳朵

只观察屏幕，Agent 仍然听不到会议、视频或系统语音中的指令。例如会议屏幕上同时显示了 `report.pdf`、`budget.xlsx` 和 `plan.docx`，有人说：“打开预算表。”单靠视觉，Agent 无法知道用户想操作哪个文件。

AOI 可以加入音频通道，但也不能把全天候原始音频持续送入语音识别模型。一个常见的第一层过滤是 VAD（Voice Activity Detection）或音量门控：

```text
没有声音
    ↓
不启动 ASR

检测到有人讲话
    ↓
开始或恢复语音转写

讲话结束
    ↓
结束当前语音片段并生成事件
```

例如：

```text
09:00:01  静音
09:00:05  检测到讲话，ASR 开始
09:00:09  识别为：“打开第二个文件。”
09:00:10  讲话结束
```

进入 Agent 上下文的不是每个音频采样点，而是一个带时间戳的语音事件：

```text
[Audio event, 09:00:05–09:00:10]
Speaker said: “打开第二个文件。”
```

VAD 只是成本控制的第一步。真实系统还可能需要区分人声和系统提示音、识别说话人、处理重叠语音，以及把语音事件和同一时间段的屏幕状态对齐。但核心原则不变：连续音频先在观察层过滤，再以离散事件进入 Agent。

## 五、关键帧不等于关键事件

如果 Agent 操作电脑一小时，可能产生数百乃至数千张截图。把它们全部放在上下文中会导致 token 数、推理延迟和缓存压力不断增加。

一个常见的压缩方式是：

```text
截图
    ↓
视觉模型理解
    ↓
生成带时间的文字描述
    ↓
保留描述，按需清理原图
```

例如：

```text
[10:22]
Gmail 收到一封来自 Bob 的邮件，主题为 “Q3 Budget”。
```

一小时的视觉历史就可以逐渐压缩成：

```text
10:01 打开 CRM
10:03 搜索客户 Tesla
10:05 找到联系人 Alice Chen
10:08 收到登录验证码
10:10 登录 Salesforce
10:15 将销售机会金额修改为 2.3M 美元
10:18 系统显示保存成功
```

这不是单纯的“把图片 OCR 成文字”，而是把多模态轨迹压缩成对任务有用的事件日志。原始截图仍可以保存在外部存储中，并通过引用重新取回。

但文字摘要不能完全替代原图。摘要适合保留长期历史和任务进度；如果下一步需要精确点击坐标、读取小字体、验证颜色或确认一个视觉细节，Agent 仍然需要请求一张新截图，或者读取 DOM / Accessibility Tree。换句话说：

> **摘要负责记住发生过什么，最新观察负责支持下一次精确操作。**

## 六、连续画面如何被压缩成稳定语义

这正是“AOI 是否依赖视频模型预训练能力”这个问题的核心。

假设画面里一个人正在吃苹果：

```text
0s  坐在桌前
1s  拿起苹果
2s  苹果靠近嘴
3s  咬一口
4s  咀嚼
5s  再咬一口
6s  放下苹果
7s  拿起手机
8s  查看手机
```

从像素角度看，每一秒都在变化；从任务角度看，1～6 秒可能只需要记成一个事件：

```text
人物正在吃苹果。
```

到了 7 秒，语义发生了边界变化：

```text
人物停止进食，开始查看手机。
```

要完成这个压缩，系统不能只识别单帧中的物体，还要理解：动作、对象、人物、时间连续性、动作阶段和常识。它需要知道“拿苹果、抬手、咬和咀嚼”可能属于同一个高层活动“吃苹果”。这就是视频预训练和时序语义先验的重要价值。

不过，工程上不应该让一个大型视频模型以 60 FPS 永久在线运行。更现实的流水线是分层的：

```text
原始视频 / 屏幕流
        │
        ▼
廉价变化检测
        │  筛掉明显无关的变化
        ▼
视觉特征或 Embedding
        │  判断语义相似性
        ▼
时间窗口聚合
        │  把连续帧组成片段
        ▼
任务相关的边界判断
        │
        ▼
VLM / Video Model
        │  只分析代表帧或关键片段
        ▼
Semantic Event
```

因此，贵模型负责确认“到底发生了什么”，便宜层负责把“哪里可能值得看”筛出来。这是一个典型的 Fast Path / Slow Path 设计。

## 七、语义去抖：AOI 判断的不是变化，而是状态边界

“一个人在吃东西”的例子还说明了另一个概念：语义去抖（Semantic Debouncing）。

按钮的 debounce 会把很短时间内的多次点击合并成一次；语义去抖则把连续的、同一含义的视觉变化合并成一个稳定状态：

```text
拿起苹果 → 咬 → 咀嚼 → 再咬 → 咀嚼
                 ↓
              吃东西
```

直到出现新的状态：

```text
吃东西 → 放下苹果 → 拿起手机
                         ↓
                      查看手机
```

这可以用三层模型来理解：

| 层级 | 需要回答的问题 | 典型方法 |
| --- | --- | --- |
| 物理变化 | 屏幕或画面变了吗？ | 像素差、光流、区域变化 |
| 视觉语义变化 | 画面内容变了吗？ | Embedding、视觉编码器、小型 VLM |
| 事件语义变化 | 发生的事情变了吗？ | 时序聚合、状态估计、VLM / LLM |

第三层最难，因为“哪些变化算一个事件”并没有固定答案。它取决于 Agent 正在完成什么任务。

同样是一个人吃苹果：

- 如果任务是监控他有没有离开房间，那么一整段可以压成“人在房间内”；
- 如果任务是分析饮食行为，那么拿起苹果、咬了几次、吃了多少都可能重要；
- 如果任务是按照教学视频执行动作，那么每个步骤边界都需要保留。

所以 AOI 最终不应该只是：

```text
screen → event
```

而应该是：

```text
screen + audio + task + history
                         ↓
                    relevant event
```

“有意义的变化”是任务相关的，而不是纯粹由像素变化决定的。

## 八、Computer Use 不应该只依赖视觉

Computer Use 有一个比现实摄像头更大的优势：它观察的是一台电脑，而电脑本身会产生大量结构化信号。

网页从 Loading 变成 Ready，不一定需要视频模型从截图中猜测。Runtime 可能同时获得：

```text
视觉：页面看起来稳定
DOM：节点连续一段时间没有变化
Network：请求已经 idle
Accessibility：Submit 按钮可点击
Window Event：目标窗口处于前台
```

多个信号共同成立时，系统更有把握把状态从 `Loading` 更新为 `Ready`。

一个更完整的 AOI 输入集合可以包括：

```text
屏幕视觉
鼠标和键盘事件
浏览器 DOM
Accessibility Tree
窗口切换
系统通知
音频和麦克风
剪贴板
文件系统事件
网络请求状态
```

这些信号可以统一成 Observation Event：

```text
WINDOW_CHANGED
Chrome → Excel

UI_CHANGED
Submit button enabled

AUDIO
“验证码是 583921”

NOTIFICATION
Download completed

FILE
report.pdf created
```

这意味着 AOI 更像一个多源状态估计器，而不是“给 LLM 接一个摄像头”。视觉是重要的兜底能力，但对于具有 DOM、Accessibility 或系统事件的电脑环境，结构化信号通常更便宜、更精确，也更容易验证。

## 九、为什么 ChatGPT 操作电脑时不会每帧调用模型

公开资料可以确认，OpenAI 的 Computer-Using Agent 会通过截图感知电脑状态，并在感知、推理和操作之间迭代；公开资料并不能证明 ChatGPT 内部已经完整采用本文定义的 AOI 架构。因此，下面是对可行工程架构的解释，不是对某个产品内部实现的断言。

关键在于：鼠标动作和模型决策不是同一个频率。

一个更接近实际的循环是：

```text
LLM / VLM 观察当前状态
        ↓
决定下一组动作
        ↓
本地 Computer Runtime 连续执行
        ├─ mouse move
        ├─ click
        ├─ keypress
        ├─ scroll
        └─ wait
        ↓
本地监控屏幕、DOM、窗口和网络状态
        ↓
判断是否到达决策边界
        ├─ 否：继续等待或执行当前动作组
        └─ 是：获取新观察并再次调用模型
```

例如模型决定执行：

```text
Settings → Network → Proxy
```

它不需要在下面这些时刻重新推理：

```text
鼠标开始移动
鼠标到达按钮
mouseDown
mouseUp
按钮颜色变化
页面淡入
spinner 转动
字体加载
```

本地 Runtime 会执行点击、等待页面切换，并持续监控环境。只有当 `Network` 页面已经出现、弹出错误、出现验证码或进入未知状态时，才把新的观察交给模型。

所以一次操作通常更接近：

```text
LLM #1
   ↓
Local execution
   ↓
页面稳定或发生重要状态变化
   ↓
LLM #2
```

而不是：

```text
鼠标每移动一点 → LLM
```

## 十、一次推理可以产生一组动作，但必须在边界处停下

如果界面状态明确，一次推理可以给出多个确定性动作：

```text
click username
type "Bob"
click password
type "..."
```

本地 Runtime 可以连续执行这些动作，再获取一张新截图或一组新的环境事件。OpenAI 的 Computer Use API 参考中也可以看到批量计算机动作的表示，这说明接口层面并不要求每个微动作都单独进行一次模型调用。

但动作不能无限批量。动作序列一旦遇到未知结果，就应该停止并重新观察：

```text
click Login
        ↓
登录成功？密码错误？验证码？2FA？网络错误？
        ↓
停止当前批次，等待新状态
```

因此可以用一个简单原则决定是否批处理：

```text
确定性连续操作       → 可以 batch
会产生未知结果的操作   → stop + observe
敏感或高风险操作       → stop + confirm
```

这里的“决策边界”同时也是安全边界。登录凭据、验证码、支付、删除或发送等动作，不能仅因为它们在动作序列中相邻，就被无条件地合并执行。

## 十一、分层控制：规划器不负责转动每一个像素

把 Computer Use Agent 和机器人控制系统类比，可以更直观地看出不同组件的职责：

```text
Level 3：Task Planner
LLM
“登录后台并修改订单。”
        ↓
Level 2：Action Planner
VLM / CUA
“打开 Orders，搜索 1234，再进入 Edit。”
        ↓
Level 1：Execution Controller
Local Runtime
“移动鼠标、点击、输入、滚动、等待。”
```

它们的频率不同：

| 层级 | 主要职责 | 典型频率 |
| --- | --- | --- |
| Task Planner | 任务分解、目标和阶段规划 | 一段任务或一个阶段一次 |
| Action Planner | 根据新页面或异常状态选择下一组动作 | 到达决策边界时 |
| Execution Controller | 把动作翻译成鼠标、键盘和等待操作 | 毫秒级连续执行 |
| Observation Runtime | 监控环境、过滤变化、生成事件 | 高频运行 |

自动驾驶系统不会让高层规划器在方向盘每转动 0.1 度时重新规划路线。Computer Use 也不应该让 LLM 控制鼠标轨迹的每个瞬间。模型负责“去哪儿”，Runtime 负责“怎样快速、稳定地到达那里”。

## 十二、AOI 更像中断控制器，而不是视频播放器

AOI 可以类比操作系统的 Interrupt Controller。

CPU 不会为了知道键盘、网卡或磁盘有没有重要消息，而每一纳秒都主动完整检查所有外设。外设持续运行，只有发生值得处理的事件时才发出中断。

同样，AOI 可以把下列变化过滤掉：

```text
页面动画       → 不 interrupt
鼠标 hover      → 不 interrupt
Loading         → 不 interrupt
页面 Ready      → interrupt
Error Dialog    → interrupt
验证码出现      → interrupt
任务结果改变    → interrupt
```

这个类比强调的不是实现细节，而是责任边界：

- 观察层持续运行；
- 事件层负责筛选和聚合；
- Agent 只在需要做决定时被唤醒；
- 模型完成决策后，执行层继续承担高速动作。

## 十三、最终架构：Fast Path 与 Slow Path

把前面的部分合在一起，一个更完整的结构是：

```text
连续环境
  ├─ 屏幕 / 音频 / DOM / 系统事件
  │
  ▼
Fast Path：廉价观察层
  ├─ 像素与区域变化检测
  ├─ VAD
  ├─ DOM / Accessibility / Network 状态
  ├─ 已知状态机
  └─ 动作执行与等待
  │
  ├─ 熟悉且稳定的状态 → 本地处理、合并或忽略
  │
  └─ 模糊、异常、任务相关变化
             ↓
Slow Path：语义理解与推理
  ├─ 关键帧或代表片段
  ├─ 语音转写结果
  ├─ 结构化环境事件
  ├─ 当前任务和历史状态
  └─ VLM / LLM 决策
             ↓
        新一组动作
```

在理想情况下，可能发生的是：

```text
1000 次物理画面变化
        ↓
100 次候选状态变化
        ↓
20 次值得记录的事件
        ↓
5 次真正需要 LLM 决策
```

这些数字只是示意，实际比例取决于任务。但“从高频原始变化逐层压缩到低频决策”的方向不会改变。

## 结语：AOI 的核心是多速率、事件驱动的观察

“AOI 是否极其依赖视频模型？”这个问题的答案需要分成两半：

如果 AOI 要从连续视觉信号中判断哪些变化属于同一个语义事件，它确实需要很强的时序语义先验，而这种能力很大程度来自图像、视频和语言上的预训练。

但这不等于让一个大型视频模型 24 小时盯着 60 FPS 的屏幕。更现实的系统会让廉价检测器负责高频过滤，让特征和时间窗口负责聚合，让 VLM / Video Model 只分析代表片段，让 LLM 只在决策边界上被唤醒；对于电脑环境本身提供的 DOM、Accessibility、窗口和系统事件，则优先使用结构化信号。

所以，AOI 最准确的描述不是“把屏幕变化转换成文字给 LLM”，而是：

> **在一个高速连续变化的电脑环境与一个低频昂贵的推理模型之间，建立一个多速率、事件驱动的感知与控制层。**

最终的计算机使用 Agent 更接近下面这条链路：

```text
Continuous Environment
        ↓
Observation Runtime
        ↓
Semantic State / Event Stream
        ↓
Decision Boundary
        ↓
VLM / LLM Reasoning
        ↓
Action Batch
        ↓
Local Execution Controller
```

前一篇关于 [Context Window、Memory 与 Harness](Context-Engineering-Agent-Harness.md) 的文章讨论了“模型本轮应该看到什么”；AOI 解决的是更早一步的问题：连续环境中“什么值得被看见、什么值得被记住、什么时候值得唤醒模型”。两者合在一起，才构成一个可持续运行的 Computer Use Agent。
