# 第十章读书笔记：多 Agent 协作

阅读来源：[《深入理解 AI Agent》第十章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter10.md)。整理日期：2026-09-08。

多个 Agent 的价值来自分工、并行、上下文隔离和独立验证。它们也会带来交接遗漏、重复劳动和资源冲突。系统是否更强，取决于组织方式带来的收益能否覆盖这些代价，而不是成员数量本身。

**1. 多 Agent 首先是在分配信息和职责**

一个 Agent 实例可以有自己的指令、工具权限、上下文和执行状态。多个实例可以使用同一个模型服务，不需要分别训练模型，也不必各自占用独立操作系统进程。

上下文是模型本次能看到的信息。共享上下文意味着后续角色继承先前历史；独立上下文则让每个角色只接收明确交接的信息。

| 方式 | 优点 | 代价 |
| --- | --- | --- |
| 共享历史、切换角色 | 能回看前序细节，交接简单 | 历史增长，旧假设可能影响新角色 |
| 独立上下文、显式交接 | 各自专注，可并行和限制信息范围 | 需要设计任务包，可能丢失重要细节 |

“不共享上下文”不等于没有共享文件；私有对话可以独立，最终产物仍可放在公共目录。反过来，共享历史也不等于拥有共同可写的全部环境。

仅仅切换写作风格或领域规则，可能加载 Skill 就足够。Skill 是按需读取的专门说明。若需要不同权限、独立检查或并行任务，独立 Agent 更合适。角色名称只是约定，真正的权限边界由运行系统执行。

**2. 协作拓扑决定控制权怎样流动**

拓扑就是成员之间的连接与调度结构。它与是否共享上下文是两个设计维度，不能混为一谈。

| 结构 | 控制方式 | 适合情况 | 主要问题 |
| --- | --- | --- | --- |
| 对等协作 | 少量角色互相反馈 | 起草与审核、辩论、专家讨论 | 反复争论、错误趋同 |
| 管理者模式 | 一个管理者分解、派发、汇总 | 多来源调研、复杂任务拆分 | 管理者判断成为瓶颈 |
| 去中心化模式 | 成员按协议自行交接与协商 | 多方独立工作、跨职责协作 | 全局一致性和终止更复杂 |

管理者统一安排的方式称为编排（Orchestration）；成员根据事件自行配合，常称为编舞（Choreography）。“Swarm”常被用于不同架构，不能仅凭名称判断是否去中心化。

管理者模式还可以分为顺序与并行。前者适合强依赖步骤；后者适合独立子任务。若流程稳定，管理者可以先生成工作流，再由程序执行调度，无需每个固定步骤都重新调用模型。

**3. 多 Agent 何时比单 Agent 值得**

独立搜索多个来源可以并行，不同模态也可以分开处理。审核者如果能运行测试或检查实际界面，还能引入生成者没有获得的新证据。Anthropic 的多 Agent 调研系统体现了这种主 Agent 与并行工作者的组织方式，同时也报告了额外资源成本。[多 Agent 调研实践](https://www.anthropic.com/engineering/multi-agent-research-system)

紧密耦合的任务则不同。例如几个人同时修改同一个核心接口，需要频繁同步，省下的执行时间可能被协调抵消。应在相近的总预算下比较单 Agent 与多 Agent，而非给多 Agent 更多计算后，把全部提升都归因于协作。

增加预算也不自动提高能力。若系统不会根据剩余时间安排探索与收敛，更多轮次可能只是重复尝试。管理者需要为子任务分配有界预算，并说明何时继续调查、何时提交已有证据。

**4. 显式交接要包含目标、约束、证据和未完成事项**

“帮我研究一下”不是可靠接口。任务包应明确范围、输入、允许操作、完成条件和返回格式。结果应包含结论、证据引用、产物位置、状态和仍不确定的内容。

例如翻译技术书，翻译者至少需要当前章节、术语表和保留代码的规则；审校者需要译文与原文，而不只是翻译者说“没有问题”的总结。管理者可以维护章节状态和文件索引，不必把所有章节全文放入自己的上下文。

Agent 间常用三种通信方式：

- 工具调用参数与返回值：适合小型、结构化任务。
- 共享文件或存储：适合较大产物与持久状态。
- 消息总线：由中间系统投递进度、结果和控制消息，适合异步协作。

异步意味着发送者不必等待对方处理完才能继续。消息应携带任务编号、发送者、消息类型和产物版本，避免不同任务或旧结果混在一起。路径只是一种引用，接收方还需要权限以及访问该版本的方式。

**5. 数据平面交换产物，控制平面管理执行**

数据平面负责文档、代码、表格等产物；控制平面负责启动、状态、取消、预算和调度。共享目录不能替代控制机制，进度消息也不能代替实际产物。

存储可以区分四类区域：

| 区域 | 内容 | 管理重点 |
| --- | --- | --- |
| 私有工作区 | 草稿、尝试、中间结果 | 隔离临时文件，明确销毁时机 |
| 任务共享区 | 正式产物、约定的进度 | 版本与并发写入 |
| 外部资源 | 用户授权的云盘或业务数据 | 源系统权限、延迟与一致性 |
| 系统资源 | 只读规则、模板与工具说明 | 稳定共享，禁止任务随意修改 |

目录名不会自动提供隔离，权限必须由存储与运行时实施。外部资源的实际一致性取决于服务契约，统一成文件接口不会改变它原有的限制。

状态最好由运行时记录，至少区分运行中、等待输入、完成与失败。进度文件适合人和模型查看摘要，完整轨迹用于排错。长时间未更新只是可能阻塞的信号，也可能正在执行长任务，不能直接判定没有进展。

**6. 取消和资源上限是协作协议的一部分**

子 Agent 被取消时，优雅终止会在安全点保存状态、释放资源并确认退出；强制终止是无响应时的兜底，可能留下未完成写入。父任务结束后，子任务通常应随之取消，确需长期运行的后台任务则要有独立生命周期。

终止条件必须对应原始目标。“找到任意一个有效答案”可以在验证后停止其他搜索；“搜集所有来源”则不能在第一份结果到达时提前结束。

总预算应覆盖所有成员，而不只是每个成员各自的上限。否则子 Agent 再创建子 Agent，总费用仍可能失控。并发额度、最长时间、步骤数和工具成本需要统一管理。

去中心化移交也要防止空转：A 交给 B，B 又交回 A。可以记录移交链与剩余预算，但正常的审核返工可能确实需要回到同一角色，因此应检测重复状态和无进展循环，而非禁止所有回访。

**7. 提议者—审核者循环怎样产生收益**

提议者生成结果，审核者依据原始要求和独立证据检查；不通过时，返回可定位的缺陷，再进入修订。Loop 工程关注怎样让这套执行、验证、记录过程持续运行，并在满足条件或遇到边界时正确停止。

审核的价值来自新增信息。代码通过测试、页面实际渲染后的截图、数据库的最终状态，都比“再读一次作者的解释”更有用。审核者也可能犯错，所以模型意见不能代替能够直接执行的确定性检查。

辩论让不同立场提出反例；头脑风暴扩大候选方案；专家小组补充不同约束。它们是否有效，取决于真实的证据与思路差异。几个实例使用相同材料并互相模仿，可能只是放大同一种错误。

独立判断可以先进行，再交换结论，减少先入为主。最终仍需按证据解决分歧，而不是把一致赞同当作真实性证明。

**8. 协作失败常发生在接口与共享状态上**

并发冲突是最直观的例子：两个 Agent 同时读旧文件再写入，后一次覆盖前一次。乐观锁通过版本检查发现冲突；版本比较和写入必须原子完成，才能避免检查之后又被修改的竞态。

跨文件语义冲突更难发现。一个 Agent 修改函数签名，另一个修改调用方但仍使用旧参数，两者可能没有任何文本合并冲突。独立 Git worktree 可以隔离编辑，最终仍需一起构建和测试。

其他常见失败包括：

- 错误级联：上游猜测经多次转述后被当作事实，应保留证据与置信边界。
- 认知趋同：成员共享相同盲点，应引入不同证据或独立验证，而不只增加人数。
- 责任推诿：目标、所有权或验收不清，应明确任务负责人和冲突裁决方式。
- 循环失控：反复辩论、重复移交或无限扩充成员，应设置预算与无进展检测。
- 理解债：产出速度超过人的理解速度，应保留可审查的设计、依据和测试结果。

崩溃故障是成员停止工作；拜占庭故障则指成员继续运行却提供错误或不一致信息。Agent 的可信错误可以借后者来理解，但普通多数投票不等于获得了正式的拜占庭容错保证，尤其当成员错误高度相关时。[原章对协作失败的讨论](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter10.md)

**9. A2A 规范协作接口，不替代质量验证**

A2A（Agent2Agent）用于不同 Agent 系统之间的互操作。Agent Card 描述能力和访问方式；Task 表达任务及生命周期；Artifact 表达交付产物。参与者可以交换进度和结果，而不暴露私有提示词与内部实现。[A2A 核心概念](https://a2a-protocol.org/latest/topics/key-concepts/)

MCP（Model Context Protocol）侧重模型应用与工具、资源的连接，A2A 侧重 Agent 之间的任务协作。两者可以配合，不能仅从调用对象是否含模型来机械区分。

标准协议便于能力发现、任务追踪和跨团队集成，但不会自动证明对方可信，也不会保证任务完成。权限、费用、验收与失败恢复仍需要明确约定。

**10. 从协作系统到 Agent 社会**

工程协作通常有一个共同目标，Agent 社会则可能包含各自不同的目标、记忆和资源。研究重点随之转向信息传播、关系形成、合作与博弈。

涌现指整体行为没有被逐步写成脚本，却从个体互动中出现。社会模拟中的活动组织、赴约和关系变化可以体现这种现象，但它们依赖模型先验、环境设定与评价方式，不能直接当作现实社会规律。

市场式协作通过报价和选择分配任务，还需要身份、交付验收和争议处理。信息不对称的游戏则要求每个成员只得到自己有权知道的状态；如果把全局信息都发给每个人，实验测到的就不再是原本的推理问题。

这些场景把同一个工程问题放大了：成员分别拥有多少信息、按照什么规则行动、怎样协调冲突，以及由谁确认最终结果。多 Agent 系统的能力，正是在这些边界上被组织出来的。
