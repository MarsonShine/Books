# 多 Agent 协作：怎样分工、交接和验证

归档任务扩展到多个部门：有的报告是扫描件，有的需要检查正文日期，全部归档后还要生成统一清单。一个 Agent 可以顺序完成，也可以把不同来源的检查交给多个 Agent。分工是否值得，取决于并行与专门处理的收益，能否抵消交接和核验的成本。

[《深入理解 AI Agent》第十章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter10.md)从上下文共享方式、协作结构、通信与控制展开，再讨论故障和 Agent 社会。本篇继续使用归档助手的教学例子，说明多个 Agent 怎样组成一个能交付的系统。

**先决定需要几份独立上下文。**

上下文是模型本次调用能够看到的指令、对话、资料和工具结果。角色切换可以沿用已有历史，例如先分析任务，再转为审核角色；也可以启动独立的子 Agent，只交给它本次职责需要的信息。

沿用历史能保留细节，但历史中的错误假设也可能影响后续判断。独立上下文让扫描件处理者专注于识别，让目录检查者专注于文件覆盖；代价是必须明确交接什么，避免漏掉共同约束。

Agent 实例不等于一个新训练的模型，也不必对应独立操作系统进程。多个实例可以使用同一个模型服务，只是指令、工具权限和状态不同。仅需切换操作规程时，加载一个 Skill 就可能足够；需要分开权限、并行工作或独立审查时，再考虑独立实例。

**分工结构决定谁来安排下一步。**

拓扑指系统中控制权和信息连接的结构。常见形式可以放到同一个任务里比较：

| 形式 | 归档任务中的安排 | 主要代价 |
| --- | --- | --- |
| 对等协作 | 执行者复制，审核者检查，双方按问题修订 | 审核可能重复，修订可能不收敛 |
| 管理者模式 | 主 Agent 分配部门任务，汇总并验收 | 分工质量依赖管理者，也可能形成瓶颈 |
| 去中心化协作 | 各角色按约定自行接手或请求协作 | 全局状态与停止条件更难协调 |

中心调度也称编排（Orchestration）；各参与者根据事件和约定自行协作，常称编舞（Choreography）。去中心化不等于无规则，也不意味着自然具备容错能力。需要明确最终交付由谁负责。

Anthropic 的多 Agent 调研系统使用主 Agent 组织并行研究，其收益与任务可拆分性有关。大量独立检索适合并行，紧密依赖同一份状态的修改则更难拆分；它也带来了额外 token 开销。[Anthropic 多 Agent 调研系统](https://www.anthropic.com/engineering/multi-agent-research-system)

**交接的是任务与证据。**

给子 Agent 的任务包可以写成：“检查财务部目录；报告期按正文认定；只读原文件；返回待归档清单、证据位置与无法判定项。”返回时至少区分完成、部分完成和失败，附上产物引用。

这样主 Agent 无需阅读每次识别尝试，也能追查某个日期的依据。文件路径只是引用，接收方还要有访问权限，并知道它指向哪个版本，不能假定另一台机器上存在相同目录。

小结果可以作为工具调用返回值传递；大产物放入共享存储；进度通知可以走消息总线。消息总线是负责投递消息的中转层，适合异步协作，也就是发送方不必等接收方处理完才继续。

消息应携带任务编号、发送者、状态、产物版本等信息。例如扫描件 Agent 报告“缺一页，等待补充”，主 Agent 才能安排恢复。没有更新不一定代表卡死；应结合心跳、当前操作和超时检查，而非只看日志文件更新时间。

**共享产物和执行控制需要分别管理。**

数据平面负责传递报告、清单等产物；控制平面负责分派、进度、取消和预算。存储可以分成私有草稿区、任务共享区、授权外部资源和只读规则区。目录名称本身不提供隔离，权限由运行时和存储系统执行。

管理者应记录哪些子任务在运行、需要输入、失败或已完成，并限制总并发、费用和轮次。停止任务时先请求子 Agent 在安全点清理资源；超过期限再使用更强的终止方式。若父任务结束，子任务是否继续，也应显式规定。

归档要求覆盖全部部门，就不能因为一个子 Agent 找到文件而取消其余任务。只有目标是“找到任意一个符合条件的结果”，并且结果已经核实，提前取消才可能节约成本。调度规则必须从验收目标推导。

**并行提高速度，但共享写入会产生冲突。**

假设两个 Agent 同时读取同一份旧清单，再分别写入自己的部门结果。后写入者可能覆盖前者，这叫丢失更新。乐观锁通过版本检查避免盲目覆盖：提交时若版本已变，先重新读取再处理。比较与写入必须由存储层原子地完成，分开“先看一眼再写”仍可能竞态。

更隐蔽的是语义冲突：一个 Agent 重命名文件，另一个在不同文件里记录旧路径。它们并未写同一个文件，单文件锁也发现不了错误。需要共同的命名约定和最终引用检查。

对归档任务，可以让子 Agent 只提交各自清单，由一个执行者统一复制；对代码任务，可以使用独立 Git 工作副本，再集中合并、测试。Git worktree 允许同一仓库有多个工作目录，但它不会自动解决逻辑冲突。

**审核需要增加证据，而不只是增加赞同。**

如果执行者报告“全部完成”，审核者只读这句话再确认，第二个 Agent 没有提供新信息。审核者应独立对照来源目录、目标文件和原始要求，指出可以定位的问题，例如“报告 B 在候选清单中，但目标目录缺失”。

提议者—审核者循环可以据此修订，但同时要有预算和停止条件：验收通过就交付；证据不足就补充；遇到无法解决的依赖或预算耗尽，应准确报告剩余工作。独立的上下文有助于减少先入为主，却不保证模型不会犯相同错误。

多 Agent 辩论、头脑风暴和专家分工可以扩大候选思路，但多数表决不能替代事实核验。三个人都引用同一条错误记录，并没有形成三份独立证据。所谓错误级联，就是一个未经核实的结论被后续步骤反复转述，最终看起来像已确认事实。

**跨系统协作需要协议。**

A2A（Agent2Agent）是 Agent 之间交换任务和产物的互操作协议。Agent Card 是能力说明，声明服务能做什么及如何访问；Task 表达进行中、需要输入、完成等状态；Artifact 表示交付产物。协作方可以使用不同实现，不必开放内部提示词和全部运行历史。[A2A 核心概念](https://a2a-protocol.org/latest/topics/key-concepts/)

MCP（Model Context Protocol）侧重模型应用与工具、资源之间的连接；A2A 侧重 Agent 之间的任务协作。协议解决交流格式和生命周期表达，任务真实性、权限和交付质量仍需系统自身验证。同一团队内部也可以采用标准协议，是否引入取决于互操作需求。

**评估整个协作系统，而不仅是每个成员。**

每个部门都返回“成功”，主清单仍可能重复或遗漏。因此既要测子任务，也要测整体验收，并与单 Agent 在可比较的总预算下对照。否则多 Agent 使用数倍资源后的提分，很难说明收益来自分工还是额外计算。

并行耗时还受依赖限制。假设三个独立检查各需两分钟，串行约六分钟；并行理想情况下约两分钟，但还要加上分派、排队和汇总。若后一个检查必须等待前一个的输出，就无法这样加速。

除成功率外，还应看总费用、重试、重复劳动和协调时间。多个 Agent 仍可能争用同一个浏览器会话、文件或服务配额，上下文独立不等于资源独立。固定流程成熟后，可以让程序负责调度，仅把需要判断的步骤交给模型。

人也需要能够理解交付件。若系统持续产出，却没人知道清单怎样生成、为什么排除某份报告，出现错误时就难以接手。这种理解落后于产出积累的负担，常被称为理解债；保留来源、边界和可读的交付说明能减少它。

**Agent 社会把问题扩展到不同目标之间的互动。**

前面的成员合作完成同一项归档任务；社会模拟中的 Agent 则可以有各自的记忆、计划和目标。涌现指没有逐步指定整体行为，却在个体互动中出现整体模式，例如信息传播或集体活动。

这类研究帮助观察合作与博弈，但模拟中的行为不能直接证明现实社会规律。市场式协作还要处理定价、交付验收与争议；信息不对称的游戏则要求每个角色只能获得自身有权知道的内容。[第十章的 Agent 社会讨论](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter10.md)

回到归档项目，可以先把独立的目录检查并行化，让最终复制与清单验收集中完成。只有当新的瓶颈确实需要更多角色、权限隔离或协作机制时，再扩大结构。每增加一个成员，都应能说明它带来了哪些新证据、并行工作或专门能力。
